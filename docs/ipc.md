# Internal IPC contracts

Status: draft v0.3 (2026-11-20), revised after two independent security reviews ("approve with changes" each; every required change is applied, and §22 records the decisions taken on the open questions of v0.1). v0.3 replaces the MAC oracle of v0.2 with failure-capped verification (§5.3, §6.15). Written **before any implementation** (execution-phase.md, "Contracts before consumers"). Nothing in this file exists in code yet.

Two contracts between hash-xcreen's own server-side processes:

1. **`hx-privd` command set** (Part 1, §3–§9): what the unprivileged `hx-gatewayd` (and the root CLI and installer) may ask the root `hx-privd` to do, over a unix socket.
2. **Session link** (Part 2, §10–§20): how `hx-gatewayd` talks to `hx-session` inside the desktop container, over a unix socket exposed into the container.

The client wire protocol is a third contract and lives in [protocol.md](protocol.md); this file only refers to it. Design background is in [architecture.md](architecture.md) §2, §4, §5, §8 and §9; the library that `hx-privd` drives is `crates/hx-provision` (its README, "Caller obligations for `hx-privd`", is binding for everything below).

Conventions: "MUST", "SHOULD" and "MAY" are used in the RFC 2119 sense. Integers outside protobuf are little-endian. Sizes are in bytes unless a unit is given. A "validation rule" is enforced by the receiver before it acts or allocates.

## 1. Trust model

### 1.1 Processes and principals

```
 client ⇄ (QUIC / WebSocket, TLS) ⇄ hx-gatewayd ──────────────┐
                                      │  privd.sock            │ Incus proxy device
 hx-agent CLI (root) ─── privd.sock ──┤  (§3)                  │ (Part 2, §11)
 installer    (root) ─── privd.sock ──┤                        ▼
                                      ▼                  hx-session (desktop user,
                                  hx-privd (root) ──► Incus      inside the container)
                                      │    unix socket
                                      └─► update fetcher, backup worker (sandboxed children)
```

| Principal | Identity on the privd socket | Trust |
|---|---|---|
| `Gateway` | uid of the `hx-gatewayd` system user | Low. Internet-facing; assume it can be compromised through a parser bug. |
| `Admin` | uid 0 (the `hx-agent` CLI, the installer, root's own tools) | Full. Root on the host is outside the threat model (architecture §8.1). |
| anyone else | any other uid | Refused at connect; no response is sent. |

`hx-session` is not a privd principal at all. It talks only to `hx-gatewayd`, over the session link, and is treated as **hostile input** there (malware in the desktop runs as the same user).

### 1.2 What a compromised gatewayd must not achieve

| Goal of the attacker | Why it fails |
|---|---|
| Run code as root | No command executes caller-supplied programs, paths, arguments, environment, recipes or Incus configuration. Every target (instance, pool, device, file, URL) is derived by privd from constants and its own state (§7). |
| Reach other containers or the host's services | Only one hash-xcreen desktop exists per server in v1, named by privd. The only device privd ever attaches is the link proxy device, whose host path privd computes (§7, rule 2). The host firewall, ACL and sysctl are generated by privd and cannot be influenced by the caller. |
| Read the Drive token, the backup key or the recovery key | They are stored root-only and loaded only by privd and the backup worker (§2). Where a client must hand one to the server, it travels sealed to a key only privd holds (§5.2). The claim is deliberately limited to *reading*: whether gatewayd could *replace* a credential is closed separately by authenticating sealed secrets with an owner key that gatewayd cannot hold (§5.2, rule 3). |
| Exhaust the host | Every command is bounded: argument limits, per-command rate limits, a global concurrency cap, per-desktop locks, deadlines, disk guards (§8). |
| Switch off isolation silently | The only commands that reduce isolation are `EnableDocker` and `allow_private_networks`. `EnableDocker` is open to the Gateway role only while the setup window is open (the wizard's `--docker` path; explicit acknowledgement, roll back on failure, fail closed); afterwards it is Admin-only. `allow_private_networks` is Admin-only. Both are logged. |
| Persist as root | Updates are accepted only if signed by an embedded minisign key, newer than the running version, and read from a root-owned copy (§6.12). privd and root tools never open paths inside a directory gatewayd can write (§7, rule 15). |

**Residual power of a compromised gatewayd** (accepted, because gatewayd is the relay by design): it sees and can drive the desktop's screen, keyboard, clipboard and files; it can read and rewrite the device registry; it can start, stop and restart the desktop, change its limits within the bounds of §6.8, change the desktop user's password (outside the setup window only with the current password, §6.9), create a few manual snapshots, disable Docker, and trigger an update to an already-verified newer release; during an open setup window it can also enable Docker (after the acknowledgement flag). That ceiling is the contract of the `Gateway` command set; any new command must justify its place in it.

**Residual risk, stated plainly.** A gatewayd compromise that stays resident in memory can add its own device to the registry and so persist across restarts as a legitimate paired device, and can capture the PIN (and, in Phase 1, the Linux password) that users type. What limits it: PIN and password verifiers are peppered with a key only privd holds, so a stolen registry cannot be attacked offline, and online guessing goes through failure-capped verification in privd (§5.3); every registry change is recorded in privd's audit log through `RecordEvent` (§6.15) and shown to all paired devices; and recovery is to rotate the identity key and revoke every device (§2.1). This is not prevented by the privd command set, because the registry is gatewayd's by design (§2).

## 2. Where state and secrets live

Decision (architecture §8.6 made concrete). Reviewed and confirmed (§22, decision 1).

| Item | Location | Owner and mode | Who reads it |
|---|---|---|---|
| **Device registry**: paired devices (public keys, names, created/last-seen), revocation state, the **peppered** PIN and Linux-password verifiers (§5.3) and failure counters, pairing-token state | `/var/lib/hx-gatewayd/registry` (the unit's `StateDirectory`) | `hx-gatewayd`, 0700 | `hx-gatewayd` only. The CLI reaches it through gatewayd's admin socket (§9), not by file. |
| Agent identity key and ACME account key | `/etc/hx/creds/*.cred`, encrypted with `systemd-creds` (TPM-backed where available) | root, 0600 | Delivered to gatewayd with `LoadCredentialEncrypted=` (tmpfs, visible to that unit only). gatewayd needs both: it terminates TLS and runs ACME. |
| **Drive refresh token, backup repository key, recovery-key material** (Phase 2) | `/etc/hx/creds/` as above | root, 0600 | `hx-privd` and the backup worker only. **Never** loaded into gatewayd. |
| privd's sealing key (§5.2): private half | `/etc/hx/creds/privd-recipient.cred` | root, 0600 | `hx-privd` only. |
| Pepper key for PIN and password verifiers (§5.3) | `/etc/hx/creds/pepper.cred` | root, 0600 | `hx-privd` only; gatewayd gets MACs, never the key. |
| Enrolled owner public key (§5.2; Phase 2) | `/var/lib/hx/owner-key` | root, 0644 | `hx-privd`. Written only by `EnrolOwnerKey` (Admin). |
| Persisted rate-limit buckets (§8) | `/var/lib/hx/ratelimit` | root, 0600 | `hx-privd` only. |
| Update staging written by the fetcher | `/var/lib/hx/updates/` | fetcher's dynamic user, 0700 | The fetcher writes; privd treats the content as hostile (§6.12). |
| privd's verified copies of artifacts | `/var/lib/hx/staging/` | root, 0700 | `hx-privd` only. |
| privd policy (max desktops, host reserve, update channel, takeover limits) | `/etc/hx/privd.toml` | root, 0644 | `hx-privd` at start. Never writable or influenceable through the socket (the channel is changed by `Admin` through the CLI, which edits this file). |
| Desktop metadata (state, username, recipe id, Docker acknowledgement, created) | Incus instance config keys `user.hx.*` | Incus | privd. After creation privd reads the username and recipe from here and never trusts the caller to repeat them. |
| Linux password | Never stored by hash-xcreen. Set inside the desktop; only the shadow hash exists, in the container. gatewayd keeps a **peppered verifier** of it in the registry (§5.3), never the password. | n/a | n/a |
| Link sockets | `/run/hx/link/` | root:`hx-gatewayd`, 0750 (§11) | gatewayd connects; it cannot create or replace entries. |
| privd socket | `/run/hx/privd.sock` | root:`hx-gatewayd`, 0660 | §3 |

Both hashes in the registry (PIN and Linux password verifier) are `HMAC(pepper, Argon2id(secret))` with the HMAC computed by privd (§5.3). Why gatewayd owns the registry: it is needed on the pre-authentication path of the internet-facing process and holds nothing that grants root (public keys and an Argon2id hash); putting it in privd would route pre-auth data through the root daemon and add a command surface for no isolation gain, because a compromised gatewayd already controls who gets in. Revocation also has to close live sessions, which only gatewayd can do. Consequences: the PIN is verified and its hash stored by gatewayd, so there is **no privd command for the PIN**; "store the PIN hash" (architecture §5.3, stage 8) is a gatewayd-local step.

### 2.1 Identity-key compromise and rotation

The agent identity key (Ed25519, architecture §8.2) is held by gatewayd because gatewayd terminates TLS. A gatewayd compromise therefore exposes it, and an attacker holding it can impersonate the server to any client that pins it. Procedure, to be implemented as `hx-agent rotate-identity` (Admin):

1. privd generates a new identity key, seals it to `/etc/hx/creds/identity.cred` (the old one is kept as `identity.prev` until step 4) and restarts gatewayd.
2. **Planned rotation** (key not believed compromised): gatewayd presents the new key signed by the old one for 7 days; clients that connect verify the signature, re-pin the new key and drop the old.
3. **After compromise**: no trust in the old key can be carried over. Every device is revoked (the registry is wiped by the CLI under the §7 rule 15 procedure) and each client re-pairs with a fresh token or the password verifier (§5.3, §9) and pins the new key. The client UI shows "server key changed" as a hard stop, never a click-through, unless the change is signed by the old key.
4. `identity.prev` is deleted after the overlap, or immediately after a compromise.

**Target design (deferred)**: a privd-backed signing oracle, so that the identity key never enters gatewayd's memory. gatewayd would implement a rustls custom `SigningKey` that sends each handshake signature request to privd over the IPC socket (rate limited, a few per second). That removes impersonation from the compromise ceiling at the cost of a new privd command and a latency step per connection; it is recorded in the Deferred list (§22), not specified here.

# Part 1: the `hx-privd` command set

## 3. Transport and peer authentication

- **Socket**: `/run/hx/privd.sock`, a unix stream socket created by systemd socket activation (`hx-privd.socket`: `ListenStream=/run/hx/privd.sock`, `SocketUser=root`, `SocketGroup=hx-gatewayd`, `SocketMode=0660`, `Accept=no`). privd inherits the fd, so it needs no filesystem permission to create it and the socket survives a privd restart (an update re-execs privd without dropping gatewayd's connection queue).
- **Runtime directories**: `/run/hx` (root:root 0755) and `/run/hx/link` (root:`hx-gatewayd` 0750, Part 2) come from `systemd-tmpfiles` (`d /run/hx 0755 root root -`, `d /run/hx/link 0750 root hx-gatewayd -`) so that they exist before any unit that needs them; the socket unit orders itself after `systemd-tmpfiles-setup.service`.
- **Peer authentication**: on every accept privd calls `getsockopt(SO_PEERCRED)`. The group bits on the socket are only a first filter. The allowlist is `{0, uid(hx-gatewayd)}`; the gateway uid is resolved by privd at start from the fixed user name compiled into the binary, never from a configuration value or from anything received over the socket. Any other uid is closed without a reply and logged. Where `SO_PEERPIDFD` exists the pid is recorded for the audit log; it is not used for decisions.
- **Self-checks at start** (privd refuses to start otherwise): the gateway user is in none of the groups `incus`, `incus-admin`, `docker`, `disk`, `sudo`, `wheel`, `adm`, `systemd-journal`, `lxd`, `shadow` or `kvm`, and has no supplementary group other than its own; no other user is a member of the `hx-gatewayd` group (membership would grant access to the privd socket and the link directory); the Incus socket is not readable by the gateway uid; `/run/hx/privd.sock` has the mode and owner above. The same checks re-run daily and after every update, and a failure sets `needs_attention=HOST_ACCOUNT_POLICY`.
- **No descriptor passing**: privd never uses received file descriptors. It reads every frame with `recvmsg` and closes the connection if the call returns any control message or `MSG_CTRUNC` (so a peer cannot make the kernel install a descriptor in privd silently, and the check is not defeated by a plain `recv`).
- **Roles**: the peer uid selects the role (`Gateway` or `Admin`) for the life of the connection. The role is never a field in a message. A command not allowed to the role is `PERMISSION_DENIED`.

## 4. Framing, messages and errors

**Framing.** A deliberate variation of `hx-proto`'s reliable-stream framing (`u32` little-endian length, then a protobuf message): the same length prefix and the same rule that a zero or oversized length, a truncated frame or a message that fails to decode closes the connection, plus one **kind** byte so that secrets can bypass the protobuf decoder (§5.1):

```
+----------------+---------+------------------------+
| length (u32 LE)| kind u8 | body (length - 1 bytes)|
+----------------+---------+------------------------+
```

`length` counts the kind byte and the body and is checked **before** anything is allocated.

| Kind | Body | Maximum `length` |
|---|---|---|
| `1` Message | one protobuf `Frame` (below) | 65 536 |
| `2` Secret | `request_id` (u64) + `slot` (u8) + raw secret bytes (§5.1) | 8 192 |

Protobuf (`prost`) is used because the rest of the project already uses it, it versions by field number, and the request/response messages are small. The messages are specified here by table; the schema is generated into the shared `hx-ipc` crate (§22, decision 9). Fields that only `Admin` may set are declared proto3 `optional`, so privd sees whether the caller *set* them: a `Gateway` request with such a field present, even at its default value, is `PERMISSION_DENIED`. Unknown fields are ignored; field numbers are never reused.

**`Frame`** (a `oneof`; exactly one variant, else invalid):

| Variant | Direction | Meaning |
|---|---|---|
| `Hello` {`major`, `minor`, `software` (≤ 64)} | caller → privd, first | Version handshake. privd requires the same `major` and answers `HelloAck`; a different major is `FAILED_PRECONDITION` and a close. Components ship from one release, so a mismatch means an update is half done and gatewayd restarts. |
| `HelloAck` {`major`, `minor`, `privd_version`, `phase` (§5.1), `role`} | privd → caller | `role` echoes the role privd derived, for diagnostics. |
| `Request` {`request_id` u64, `deadline_ms` u32, `secret_slots` (repeated `SecretSlot`), `command` (`oneof`, §6)} | caller → privd | `request_id` is chosen by the caller, non-zero, unique on the connection (a repeat is `INVALID_ARGUMENT`). `deadline_ms` may only shorten the command's maximum deadline (§8); 0 means the maximum. |
| `Cancel` {`request_id`} | caller → privd | Cancel the in-flight request; an unknown id is ignored. |
| `Ping` {`nonce` u64} / `Pong` {`nonce`} | both | Connection-level liveness (this replaces a `Ping` command). Answered at once, even while a request is running; at most 10 per second. |
| `Progress` {`request_id`, `stage`, `index`, `total`, `step` (≤ 128, sanitized), `percent` (0–100 or 255 for unknown), `ok`} | privd → caller | Zero or more per request, before its `Response`. |
| `Response` {`request_id`, `result` (`oneof`: a per-command result or `Error`)} | privd → caller | Exactly one per request. |

**Connection rules.** `Hello` within 5 s of accept, else close. The body of a frame must arrive within 5 s of its header. A connection idle for 10 minutes is closed (callers reconnect). privd allows **one request in flight per connection**; a second `Request` before the `Response` is `RESOURCE_EXHAUSTED`. `Cancel`, `Ping` and `Pong` are the only frames accepted while a request runs. Parallelism comes from several connections (§8). Requests are processed in arrival order per connection.

**Cancellation.** `Cancel`, a closed connection and an expired deadline cancel the running command at its next *safe point*:

- **Secret-carrying sections are shielded.** A section that handles a secret (`run_post_stage` with the password, `SetUserPassword`, the current-password check, `PepperVerify`, `PepperEnrol`) runs to completion, bounded by its own timeouts, and its work directory is swept; only then does privd answer `CANCELLED` or `DEADLINE_EXCEEDED`. A cancel never lands between writing the secret file and removing it.
- **Everything else is cancellable, and cancel is explicit.** Dropping an `hx-provision` future does not stop an Incus background operation. On cancel privd therefore deletes the Incus operation it started (`DELETE /1.0/operations/<id>`) and **waits for it to end** (at most 30 s) before it runs the command's cleanup (§6.5 for `CreateDesktop`) and answers. If the operation will not end, privd answers `INTERNAL` and sets `needs_attention=STUCK_OPERATION` rather than start new work on the same desktop.
- A cancelled command never leaves state it did not own; the "converge" semantics below make a retry safe.

*hx-provision follow-up (1D):* a cancel-safe secret path (the post stage as one shielded unit) and an API that exposes the Incus operation id so that it can be cancelled (§21).

**Progress streaming.** Long commands (`SetupHost`, `CreateDesktop`, `EnableDocker`, `ApplyUpdate`, Phase 2 backups) emit `Progress` frames. They map `hx_provision::Progress` (`Started`/`Finished` with `stage`, `index`, `total`, `step`, `elapsed`, `ok`) one to one and add coarse stages not in that type:

`stage` ∈ `PREFLIGHT`, `HOST`, `IMAGE_FETCH`, `IMAGE_IMPORT`, `BUILD`, `LAUNCH`, `POST`, `DOCKER`, `SESSION`, `UPDATE`, `BACKUP`, `RESTORE`, `DONE`.

Progress is lossy and bounded: at most 10 per second per request, at most 256 buffered per connection; when the peer reads slowly privd keeps the newest and drops the rest. A step description is `hx-provision`'s own text (recipe-defined, never container output), still passed through `sanitize`. The `Response` is never dropped; if the peer will not read it within 10 s privd closes the connection (the command's effect stands).

**Error model.** `Error` {`code`, `detail` (command-specific enum, optional), `message` (≤ 256 bytes, sanitized, never contains secrets or unsanitized container output), `retryable` (bool), `retry_after_ms`, `stage` (optional: the failing stage of a long command, §6.5)}.

| `code` | Meaning |
|---|---|
| `INVALID_ARGUMENT` | A validation rule failed. `message` names the field. |
| `PERMISSION_DENIED` | The role may not call this command, or the command may not take this argument from this role. |
| `FAILED_PRECONDITION` | Wrong state: setup window closed, desktop not ready, `needs_attention` set. `detail` says which. |
| `NOT_FOUND` | Unknown desktop or snapshot id. |
| `RESOURCE_EXHAUSTED` | Rate limit, concurrency cap, host headroom, pool space, desktop cap. Retryable with `retry_after_ms` where known. |
| `DEADLINE_EXCEEDED` / `CANCELLED` | Deadline hit or `Cancel` received. |
| `UNAVAILABLE` | Incus (or another dependency) cannot be reached. Retryable. |
| `UNIMPLEMENTED` | Command reserved or not available in this release. |
| `INTERNAL` | A bug or unexpected dependency failure; the detail is in the journal, not in the message. |

A *domain outcome* that the caller must act on is a successful `Response`, not an `Error` (for example Docker's `SelfTestFailed`, §6.9). Container-originated text is sanitized by `hx-provision` (control and ANSI characters removed, truncated) and is still untrusted: callers escape it for any UI.

## 5. Authorization and secrets

### 5.1 Command classes

privd authorizes by role and by **phase** (kept in `/var/lib/hx/privd-state`, root-only, one of `UNINITIALIZED`, `SETUP_OPEN`, `READY`; plus independent `needs_attention` flags per desktop, §6.9).

| Class | Gateway | Admin |
|---|---|---|
| `R` read-only | always | always |
| `A` routine (desktop operations) | when `READY`, or during `SETUP_OPEN` | always |
| `S` setup | only while `SETUP_OPEN`, with the restricted argument set | always, full argument set |
| `X` privileged | never | always |

`SetupHost`, `CreateDesktop` and **`EnableDocker`** are class `S`: after the window closes they are effectively class `X` (Admin only, for Docker through `hx-agent docker enable`; a later design may accept an owner-key-signed request from the app, which needs the owner-key enrolment of §5.2). `DisableDocker` stays class `A` because it only reduces exposure.

`SETUP_OPEN` is opened only by `Admin` (`BeginSetup`, called by the installer after it has verified and installed the agent), lasts **2 hours by default**, and can be extended only by `Admin` (`ExtendSetup`, up to 24 hours in total) or closed by `FinishSetup` (callable by Gateway or Admin once a desktop is `ready`). The window exists for the one-liner path, where the app drives the install over the paired channel (architecture §5.3 stages 4 to 8) without gatewayd keeping standing power to create desktops or rebuild the host afterwards. **In the SSH install path the window is not needed for secrets**: the app sends the password and the Drive token over SSH to the root installer, which calls privd as `Admin` and writes the verifiers through the gatewayd admin socket (§9), so gatewayd never sees them. The window limits the damage from a gatewayd compromised *after* setup; it does not protect a compromise *during* setup, which is why the setup commands take only bounded, validated arguments anyway.

Stages the installer (root) performs itself, outside privd, because they change host packages and the host firewall policy: stage 4's *install Incus* (package manager; the sysctl file and later steps are privd's, §6.4) and stage 6 (*open the agent port* in ufw or nftables). privd never opens a port.

### 5.2 Secrets: how they travel and are held

Rules for every secret (Linux password, PIN-related MAC inputs, Phase 2 Drive token and backup key): never in argv, environment, a file path, a log line, an error message, a `Progress` step or a protobuf message; never written to disk by privd except the declared swept work file inside the container (§6.9).

1. **Secret frames.** A request that carries secrets lists them in `secret_slots` and sends one **kind `2` frame** per slot straight after the `Request` and before processing begins. `SecretSlot` = {`slot` u8, `kind`, `sealed` bool, `length` u32, and fields **reserved now** for the Phase 2 sealed form: `upload_nonce` (16 bytes), `signer_key_id` (u32)}. privd reads these frames into `Zeroizing` buffers and excludes them from core dumps (`PR_SET_DUMPABLE=0` for the whole process, `RLIMIT_CORE=0`), without passing them through `prost`, so the protobuf decoder makes no copy of them. **Swap is prevented process-wide, not per buffer**: privd and gatewayd both call `mlockall(MCL_CURRENT | MCL_FUTURE)` at start (the unit sets `LimitMEMLOCK=infinity`; a failure to lock is fatal), because per-buffer `mlock` cannot cover the frame buffer the decoder allocates. Both **must read the privd and admin sockets with `Decoder::read_from` over a `NoCmsgReader`** (no intermediate user buffer). The copies of a secret that then exist, and nothing else: (1) the kernel's socket buffer, until `recvmsg` returns (outside the process, discarded by the kernel); (2) the decoder's frame buffer, filled directly by `recvmsg`, zeroized by `SecretFrame::from_body` right after the copy below, and zeroized on drop or poison if the frame is cut short; (3) the `Secret` (`Zeroizing<Vec<u8>>`, not `Clone`, redacting `Debug`), zeroized on drop. `hx-ipc`'s `tests/alloc.rs` asserts that decoding a kind-2 frame makes exactly the two allocations of (2) and (3). On the sending side `encode_secret` and `SecretFrame::encode_body` return `Zeroizing` buffers. What a caller does with `Secret::expose()` afterwards (the stdin file of `chpasswd`, the Argon2 input) is outside this crate and is swept by privd. (The kernel's socket buffers and the read buffer still hold the bytes briefly; the read buffer is zeroized after use, and the point of the design is that no *long-lived or pooled* heap copy exists, not that no copy ever exists.) Missing, extra, oversized or late (5 s) secret frames reject the request. The `Request` struct has no field that can hold secret bytes, and secret types have a redacting `Debug`.
2. **Where each secret goes.**

| `kind` | Accepted forms | Length | Use |
|---|---|---|---|
| `USER_PASSWORD` | plain, or sealed | 1–1 024 bytes, no `\n`, `\r` or NUL (the `hx_provision::Secrets::with_user_password` rules) | stdin of `chpasswd` via `hx_provision`'s 0600 file in the 0700 work directory (no argv, no environment), then swept |
| `CURRENT_PASSWORD` | plain | same | Checked against the desktop user's shadow hash before `SetUserPassword` outside the setup window (§6.9), through the same stdin-file path, then swept |
| `MAC_INPUT` | plain | exactly 32 bytes | The Argon2id output that `PepperVerify` compares and `PepperEnrol` MACs (§5.3) |
| `DRIVE_TOKEN` (Phase 2) | **sealed only** | at most 8 182 (the kind-2 limit of 8 192 minus the kind byte and the 9-byte `request_id` and `slot` header) | Sealed into privd's credential store; handed to the backup worker as a repository handle, never as the raw token (architecture §9.4) |
| `BACKUP_KEY` (Phase 2) | **sealed only** | at most 8 182 | As above |

3. **Sealed secrets (Phase 2; the shape is fixed now so that nothing changes later).** The Drive token and backup key are sealed by the client to privd's recipient key and **authenticated by an owner key**, so that gatewayd can neither read them (confidentiality) nor substitute its own (integrity). Format: HPKE (RFC 9180) **Auth mode** (`mode_auth`) with DHKEM(X25519, HKDF-SHA256), HKDF-SHA256 and ChaCha20-Poly1305; the sender's static key is the **owner key**; `info` = `hx-privd-secret/v2`; `aad` = `len(desktop_id)` (u8) ‖ `desktop_id` ‖ `kind` (u8) ‖ `upload_nonce` (16 bytes); plaintext = `not_after_unix_s` (u64) ‖ value. (A signature by the owner key over the same fields plus the ciphertext is an acceptable alternative construction; the requirement is the properties, below.)
   - The **owner key** is a keypair held by the user's client. Its public half is enrolled in privd **outside gatewayd's control**: by `EnrolOwnerKey` (Admin) called by the installer over SSH during setup, or by `hx-agent owner enrol` on the server. privd refuses a sealed secret that is not authenticated by the enrolled owner key. Without an enrolled key, `SetBackupCredentials` is `FAILED_PRECONDITION` and the Drive token must be set through the CLI.
   - The **`upload_nonce`** is issued by privd (`BeginSecretUpload` {`kind`, `desktop_id`} returns 16 random bytes; one-time, bound to kind and desktop, expires in 10 minutes, consumed on first use). It makes replay of a captured box useless, and the length-prefixed `desktop_id` stops ambiguity between ids.
   - privd rejects a box whose `not_after` has passed.
   - **Delivery of privd's recipient public key** (`GetRecipientKey`, §6.2): over SSH where the SSH install path is used (authentic, because the SSH host key was confirmed); otherwise through an authenticated hook in the pairing exchange, which belongs to 1B and is the remaining dependency for the one-liner path.
   In Phase 1 only the Linux password exists. It may travel plain: gatewayd then sees it in memory in transit in the one-liner path (decision Q2, §22) and never in the SSH path.
4. **Gateway-side obligations.** `hx-gatewayd` holds a password or PIN only between receiving it from the client and the privd response, in `Zeroizing` memory, with no copy into logs, metrics or panics (a panic hook redacts). gatewayd runs with `PR_SET_DUMPABLE=0` and `LimitCORE=0` (and `MemoryDenyWriteExecute`, `ProtectProc=invisible` where compatible), so an unprivileged process cannot ptrace it or read its memory, and a crash writes no core. If gatewayd restarts mid-install the app resends the password; nothing is stored for resuming.
5. **Process hygiene.** privd and the workers it spawns are started with a cleared environment and fixed argv from constants (never through a shell); nothing derived from a secret appears in `/proc/<pid>/cmdline`, `environ`, a unit file or the journal. This is what Gate 1's "no secret in any command line, log or process list" checks. **One-liner token (decision 14, §22; owner 1E and the wizard):** the one-liner carries **no token**. The installer prompts for it on `/dev/tty` with hidden input and hands it to gatewayd as the `CreatePairingToken` secret frame (§9). `--token` in argv remains only for unattended use and is documented as weaker: `sudo` writes the argv to the auth log and the journal, and the shell keeps it in its history; the token is single-use and expires after 15 minutes, which bounds but does not remove that exposure. Gate 1 applies to the installer's own argv, so the interactive prompt is the default the wizard produces.

### 5.3 Verifier hashes and the pepper

Decision (§22, decision 1). gatewayd keeps **two verifiers** in the registry, both of the form `HMAC-SHA256(pepper_purpose, Argon2id(secret, salt))`:

- the **PIN verifier**, used on every connection (architecture §8.3);
- the **Linux-password verifier**, set whenever the password is set through hash-xcreen (`CreateDesktop`, `SetUserPassword`, the installer in the SSH path), used for re-pairing after a lockout (architecture §8.3: "re-pairing needs the password") and for the web client's first login (Phase 3). A password changed inside the desktop with `passwd` makes the verifier stale: re-pairing by password then fails, and the user resets it with `hx-agent password reset` (Admin; it recomputes the verifier).

The Argon2id step runs in gatewayd (it has the CPU budget and the parameters live in `hx-crypto`). The pepper step runs in privd and is split in two commands, so that **no command returns a MAC to a caller that could use it as a guessing oracle**:

- **`PepperVerify`** (§6.15) answers only *yes or no* for a given input and expected verifier, and **counts failures globally per purpose**. This is the only operation gatewayd performs on a login path.
- **`PepperEnrol`** (§6.15) returns the MAC, only so that a verifier can be set or changed; it is limited to a few calls a day for Gateway after setup.

A stolen registry (or a memory dump of a past gatewayd) therefore cannot be attacked offline without privd's pepper, and an *online* attack, even from a fully compromised gatewayd holding the registry, is limited to the failure caps below: a 6-digit PIN or a dictionary password cannot be guessed at any useful rate. The pepper is per purpose (`pin`, `password`), derived with HKDF from `/etc/hx/creds/pepper.cred`.

**When gatewayd may call `PepperVerify`.** For the PIN, only after the device has authenticated with its pinned key in the TLS handshake (so only the holder of a paired device key can cause a PIN check, and gatewayd's own per-device lockout of 5 failures applies first, architecture §8.3). For the password, only inside a re-pair or web-login flow that gatewayd already rate limits per source address. Successful verifications are free; they do not count against any cap.

**Failure caps (global per purpose, persisted across restarts, §8):** `PIN` 10 failures per hour and 50 per day; `PASSWORD` 5 per hour and 20 per day. A `CURRENT_PASSWORD` check (§6.9) has its own cap of 20 checks per day and charges every failure to the same `PASSWORD` budget. Past a cap that purpose is **locked**: every `PepperVerify` for it answers `RESOURCE_EXHAUSTED` (detail `LOCKED`), `needs_attention` gets `PIN_LOCKED` or `PASSWORD_LOCKED`, the event is audited, and only `Admin` can lift it (`ResetLockout`, §6.13).

**Trade-offs, stated.**
- The `PASSWORD` failure cap is a lockout lever that an internet attacker can pull once web login exists (Phase 3): enough wrong password attempts through the web login lock the password re-pair and web-login path until an Admin resets it. Only that path is locked (device-key PIN login and existing sessions continue to work), and the cost is accepted in exchange for making password cracking impractical. The PIN cap cannot be pulled by an unauthenticated attacker, because `PepperVerify` for the PIN is only reached after device-key authentication.
- PIN checks depend on privd's availability: while privd re-execs during an update, a login can fail briefly (`UNAVAILABLE`, retry); gatewayd tells the client to retry and does not count it as a wrong PIN.

**Regression tests required (1C):** (1) a loop of wrong `PepperVerify` guesses hits `RESOURCE_EXHAUSTED` and then the `LOCKED` state within the cap, and the lock **survives a privd restart**; (2) correct verifications never consume the failure budget; (3) `PepperEnrol` from Gateway after setup is refused past its daily cap, allowed more often during `SETUP_OPEN`, and never limited for Admin; (4) no command returns a MAC except `PepperEnrol`.

## 6. Commands

Common to every command: arguments are parsed into typed values at the boundary (parse, do not re-validate later; the typed value is what is used) and an argument not listed is ignored. **Converge** means the command drives the system to the described state and succeeds if it is already there. All mutating commands are written to the audit log (§8) with role, command, desktop id and outcome, never with argument values that could be secret.

Shared types:

- `DesktopId`: `^[a-z][a-z0-9]{0,11}$`. v1 allows exactly one desktop and the installer uses `main`. privd maps it to the instance name `hx-<id>`; the caller never supplies an instance name (hx-provision README, "Names and paths stay inside privd").
- `Limits` {`cpu` u32, `memory_mib` u64, `disk_gib` u64}; bounds in §6.8. `limits.processes` is not settable (always `DEFAULT_PROCESSES` = 8192, never unlimited).
- `Distro` ∈ `ubuntu-24.04`, `ubuntu-26.04`, `debian-12`, `debian-13`; `Desktop` ∈ `xfce`; `Preset` ∈ `basic`, `developer` (the `hx_provision::{Distro, Desktop, Preset}` enums; unknown values are `INVALID_ARGUMENT`).
- `Username`: `hx_provision::Username::new` (1–32 characters of `^[a-z_][a-z0-9_-]{0,31}$`, reserved names refused).

### 6.1 Liveness (frames `Ping` / `Pong`, not a command)

Handled at the connection level (§4); no request, no class, no role check beyond being a served peer.

### 6.2 `GetHostInfo` (R, both)

Returns the facts the app and the installer's preflight show: `privd_version`, `phase`, OS id and version, arch, CPU count, total and available memory (MiB), pool {exists, driver, total and free GiB}, Incus version (`Client::server_info`), `docker_on_host`, `host_firewall_loaded` (table `inet hx` present), `sysctl_ok`, `needs_attention` list, and whether a desktop exists. Read-only; deadline 10 s. Failure: `UNAVAILABLE` if Incus is down (the other fields are still returned in the success body with `incus` marked absent).

**`GetRecipientKey`** (class R, both) {} returns `{key_id, public_key (32 bytes, X25519), owner_key_enrolled}`: the key to which sealed secrets are encrypted (§5.2). It involves no secret; the client must obtain it through an authenticated path (SSH, or the pairing hook), not trust the copy gatewayd relays.

### 6.3 `BeginSetup` / `ExtendSetup` / `FinishSetup`

- `BeginSetup` (class X) {`expires_in_s` 60 to 86 400, default **7 200 (2 hours)**}: Admin only; `UNINITIALIZED` or `READY` to `SETUP_OPEN`.
- `ExtendSetup` (X) {`extend_by_s` 60 to 86 400}: Admin only; the total lifetime of one window never exceeds 24 hours.
- `FinishSetup` (A) {}: Gateway or Admin; `SETUP_OPEN` to `READY`; requires that at least one desktop in state `ready` exists unless called by Admin with `force`.

All converge. The window state is also mirrored into gatewayd through the admin socket (§9) so that gatewayd itself refuses setup traffic from clients when no window is open (defence in depth; privd is the authority).

### 6.4 `SetupHost` (class S)

Purpose: what architecture §4.2 and §5.3 stages 4 to 6 require on the host, except the two steps that belong to the root installer (installing Incus with the package manager in stage 4, and opening the agent port in stage 6, §5.1): `ensure_host` (pool, bridge, ACL, profiles), the sysctl file, the nftables host ruleset and the Docker `DOCKER-USER` rules.

| Argument | Type and validation | Who |
|---|---|---|
| `pool_size_gib` | u32, 12–200 (`MIN_POOL_GIB`/`MAX_POOL_GIB`); default `default_loop_size_gib(free)`; also at most 60% of the free space of the Incus storage directory's filesystem at call time. Maps to `PoolSource::LoopFile`. | Gateway, Admin |
| `pool_device` | A block-device path under `/dev/`. privd itself verifies, as root, what the README demands of the installer: it is a block device (not a symlink target of a non-device), a whole disk, not mounted, no mounted or in-use partitions, no filesystem or RAID/LVM signature (`blkid -p`), not the device holding `/`. Maps to `PoolSource::Device`. | **Admin only** |
| `allow_private_networks` | bool, default false. Maps to `HostSpec::allow_private_networks`; reducing isolation, so installer option only. | **Admin only** |
| `extra_host_addresses` | up to 16 IPs. | **Admin only** |
| `ipv4` | `auto` or `a.b.c.d/nn` (`/16`–`/29`, a private range). Default `auto`. | **Admin only** |

privd does:

1. `HostSpec`: `Naming::production()` (never a caller prefix), `host_addresses` = **every** address of every interface except our own bridge, enumerated by privd over netlink (public, private, Docker bridge gateways), plus `extra_host_addresses`; `HostSpec::validate()`.
2. `hx_provision::ensure_host`. Idempotent; nothing is deleted.
3. Take `HostReport::host_firewall` (privd calls `nft_host_protection` itself; the text is never accepted from a caller), check it with `nft -c -f -`, load it with `nft -f -` (the ruleset on stdin), and persist it to `/etc/hx/host-firewall.nft` with a oneshot unit `hx-host-firewall.service` that loads it at boot, ordered before `incus.service`. Done when `nft list table inet hx` shows the table.
4. Write `/etc/sysctl.d/90-hx-incus.conf` from a constant template (`fs.inotify.max_queued_events`, `max_user_instances`, `max_user_watches` = 1048576; `vm.max_map_count` = 262144) and apply it with `sysctl --system` (architecture §5.3 stage 4); verify by reading the values back.
5. If a host Docker is present (the `DOCKER-USER` chain exists): ensure the two accept rules for our bridge (`iptables -C` then `-I`, idempotent) and install `hx-docker-user.service`, ordered after `docker.service`, which re-applies them. If the rules cannot be applied, the response says so (`docker_user_rules: FAILED`) and `needs_attention` gets `HOST_DOCKER_FORWARDING`; the command still succeeds, because the desktop works without internet and the installer decides.

privd also re-runs steps 1 to 3 on its own at start and, after a 30 s debounce, whenever a host address appears or disappears (the README requires `ensure_host` to be re-run when `host_addresses` change). That is internal behaviour, not a command.

Output: `{pool, network, acl, desktop_profile, compat_profile` (each `Ensured`: created/existed/updated)`, gateway_ip, firewall_loaded, sysctl_applied, docker_user_rules}`. Idempotent (converge). Deadline 5 minutes. Progress stage `HOST`. Failure: each step is independently idempotent, so a failed `SetupHost` is simply called again; the error names the step (`detail` ∈ `POOL`, `NETWORK`, `NFT`, `SYSCTL`, `DOCKER_USER`). Incus down is `UNAVAILABLE`.

### 6.5 `CreateDesktop` (class S)

Purpose: create the desktop container, from a prebuilt image or by building on the server (architecture §4.3), through to `ready`.

| Argument | Type and validation |
|---|---|
| `desktop_id` | `DesktopId`. Refused if a desktop already exists (v1 cap, from `privd.toml`, default 1) unless this is a retry of the same id still in state `creating`/`failed`. |
| `distro`, `desktop`, `preset` | enums as above. |
| `username` | `Username`. |
| `image_mode` | `AUTO` (default), `PREBUILT`, `BUILD`. |
| `limits` | `Limits`, bounds in §6.8; omitted fields get privd defaults (all host CPUs; memory = host RAM minus the reserve; disk = 80% of the pool). |
| `docker` | bool, default false (the wizard's `--docker`). If true, `docker_isolation_acknowledged` MUST also be true and the Docker flow of §6.9 runs after the post stage. Like every `CreateDesktop` call from Gateway it is possible only while the setup window is open. |
| `settings` | `hostname` (RFC 1123 label), `timezone` (a name present in `/usr/share/zoneinfo`), `locale` (`^[a-z]{2,3}_[A-Z]{2}(\.UTF-8)?$` from an allowlist), `keyboard` (`^[a-z]{2}(\+[a-z0-9_-]{1,16})?$`). **Reserved**: the recipe vars for these do not exist yet in `hx-provision`, so a non-empty `settings` is `UNIMPLEMENTED` until 1D adds them (§21). |
| `image_file` | **Admin only** (proto3 `optional`, §4): path of an offline image under `/var/lib/hx/import/`, opened `O_NOFOLLOW`, a root-owned regular file, signature and checksum verified. Gateway: `PERMISSION_DENIED`. |
| secret slot 0 | `USER_PASSWORD`, required (plain or sealed, §5.2). |

privd does:

1. Authorize (class S), take the `desktop:<id>` lock, check the phase and the desktop cap, check free pool space against a minimum (≥ 8 GiB free and ≥ 15% free).
2. Load the recipes that are **embedded in the privd binary** (`Catalog::embedded()`, an `hx-provision` follow-up, §21; recipes are then covered by the agent's signature and no directory is read at all); **never** `Catalog::from_dir`. `Catalog::resolve_for(RecipeId, addons, Some(&username))`.
3. Choose the image path (`AUTO`: reachability of the release host, free disk, download speed against the apt mirror; reason recorded). Download and signature/checksum verification of a prebuilt image is done by the sandboxed fetcher (§6.12) plus privd's own minisign and SHA-256 verification; privd imports it through the Incus REST API. The base image for the build path is a constant remote alias (`ImageSource::Remote` with a constant server, never a caller value).
4. `DesktopSpec::for_plan(name = "hx-<id>", Naming::production(), &plan, limits)`, `compat_profile` from `needs_compat_profile(&plan)`, then `orchestrate::finish_prebuilt` (prebuilt) or `orchestrate::build_on_server`. The post stage runs through `run_post_stage` (which sweeps `/run/hx-provision` before and after) with `Secrets::with_user_password`. The call must never be `apply_stage(.., Stage::Post, secrets, ..)` directly (README).
5. Write instance metadata: `user.hx.state=creating` first, then `user.hx.username`, `user.hx.recipe`, `user.hx.created`; `user.hx.state=ready` **last**, after steps 6 and 7 succeed.
6. Provision the session link (§6.10) and install `hx-session` (§6.10), so the version matches the agent.
7. Optional Docker (§6.9).

Idempotency and failure: a retry with the same `desktop_id` and arguments while the desktop is `creating` or `failed` destroys that unfinished instance (`destroy_instance`; it holds no user data yet) and starts again; a `ready` desktop with the same arguments returns success with its current report; with different arguments, `FAILED_PRECONDITION`. On any failure or cancel privd destroys the instance it created in this request, so no half-built desktop is left behind, and the error carries the failing stage. Output: `{desktop_id, path_taken: PREBUILT|BUILD, reason, timings, warnings (≤ 16, each ≤ 256 bytes, sanitized), docker (the §6.9 outcome, if requested)}`. Deadline 45 minutes (targets: prebuilt < 5 min, build < 20 min). Rate: 3 per hour. Progress stages `PREFLIGHT`, `IMAGE_FETCH`, `IMAGE_IMPORT`, `BUILD`, `LAUNCH`, `POST`, `SESSION`, `DOCKER`.

### 6.6 `GetDesktop` / `ListDesktops` (R, both)

`GetDesktop` {`desktop_id`} returns `{desktop_id, state (creating|ready|failed|stopped|running|starting), username, distro, preset, ip (bridge address), limits, docker (off|on|degraded), needs_attention[], session {installed_version, link_provisioned}, snapshots (count), created}` from `Client::get_instance`/`instance_state` and the `user.hx.*` keys. `ListDesktops` returns at most 8 of these. Deadline 10 s. `NOT_FOUND` for an unknown id.

### 6.7 `StartDesktop` / `StopDesktop` / `RestartDesktop` (class A)

{`desktop_id`, and for stop and restart `force` bool (default false)}. Calls `Client::set_state` (`Start`, `Stop`, `Restart`) with a 30 s graceful timeout; `force` skips the grace period. Converge: starting a running desktop succeeds. After a start privd waits for `wait_system_running` (60 s, `allow_degraded=false`) and reports `{running, degraded}`. Refused with `FAILED_PRECONDITION(ISOLATION_NOT_RESTORED)` for Gateway while that flag is set (§6.9); Admin's `StartDesktop` retries the rollback first. Deadline 2 minutes. Rate: 6 per minute per desktop.

### 6.8 `SetLimits` (A)

{`desktop_id`, `limits`}. Bounds, computed by privd from the host at call time:

- `cpu`: 1 ≤ cpu ≤ host CPU count.
- `memory_mib`: ≥ 1 024 and ≤ host RAM − max(1 536 MiB, 25% of host RAM) (headroom for the host and Incus).
- `disk_gib`: ≥ the desktop's current usage plus 2 GiB (never shrinks below use), ≤ pool free space. Not zero in any field.

`hx-provision` itself enforces only "not zero" (`DesktopSpec::to_create`); **all of the bounds above are enforced by privd before it calls Incus**.

Applies `limits.cpu` and `limits.memory` with `Client::patch_instance_config` and the root disk size through the instance's root device (live where Incus allows; the response says `restart_required`). Never touches `limits.processes` or any other key. Converge. Deadline 30 s. Rate: 6 per hour.

### 6.9 `SetUserPassword`, `EnableDocker`, `DisableDocker`

**`SetUserPassword`** (class A) {`desktop_id`; secret slot 0 `USER_PASSWORD`; slot 1 `CURRENT_PASSWORD` required unless the setup window is open}. privd reads the username from `user.hx.username` (a caller-supplied name is not accepted). Outside `SETUP_OPEN` it first verifies `CURRENT_PASSWORD` against the desktop user's shadow hash with a fixed helper exec inside the container (the password reaches it only as stdin through the same swept 0600 file as `chpasswd`; no argv or environment), at most 20 checks per day, each failure charged to the shared `PASSWORD` failure budget of §5.3 (5 per hour, 20 per day, persisted, §8), and a locked `PASSWORD` purpose refuses the check; a wrong current password is `PERMISSION_DENIED`. The check is **a fixed-argv helper shipped in privd's verified `hx-session` package** (a small static crypt/yescrypt checker), and privd trusts only its **exit status**, never its output. This stops a compromised gatewayd from locking the user out of their own desktop or taking it over without ever knowing the password. It then changes the password through the bounded path of the post stage. The whole section is shielded against cancellation (§4). On success gatewayd refreshes its password verifier (§5.3). Converge (setting the same password is a no-op in effect). Rate: 10 per hour. Failure: `FAILED_PRECONDITION` if the desktop is not running. *Gap in hx-provision: it has no standalone "check and set password" entry point, only the post stage; §21.*

**`EnableDocker`** (class S, therefore Admin-only once setup is over; §5.1) {`desktop_id`, `acknowledged_isolation_warning` bool (MUST be true, else `INVALID_ARGUMENT`), `mode` ∈ `STANDARD` (default), `HOST_NETWORK_ONLY` (reserved: `UNIMPLEMENTED` until hx-provision supports it)}. After setup the call is `hx-agent docker enable`. privd records the acknowledgement time in `user.hx.docker_ack`, resolves the add-on with `Catalog::resolve_addon_for(id, Addon::Docker, Some(&username))` and calls `docker::enable_docker(.., DockerOptions::default(), ..)`. `allow_old_incus` is never set from a request (the field does not exist). The `DockerOutcome` is returned as a normal response:

- `Enabled {docker_version}`.
- `UnsupportedIncus {found, required, fallbacks}`: nothing was changed.
- `SelfTestFailed {isolation_restored, hint, output_tail (sanitized, at most 2 KiB), fallbacks}`.

**Fail closed.** If `isolation_restored` is false privd retries the rollback itself up to 3 times (the three allowed keys back to off, then restart). If it still fails, privd stops the desktop, sets `needs_attention=ISOLATION_NOT_RESTORED`, and refuses `StartDesktop` from Gateway until the rollback succeeds (Admin's `StartDesktop` retries it). This is the explicit handling of `DockerOutcome::SelfTestFailed::isolation_restored` that the README requires. Fallback 1 (Zabbly Incus) is class X (`UpgradeIncus`, §6.13); fallback 2 is reserved. Converge: an already-enabled desktop that passes the self-test returns `Enabled`. Deadline 15 minutes. Rate: 3 per hour. Progress stage `DOCKER`. Reason for the class: enabling Docker lowers container isolation, and a compromised gatewayd must not be able to do that on its own after setup (§7, rule 5).

**`DisableDocker`** (A) {`desktop_id`}. Sets `security.nesting` and the two syscall intercepts back off (the three keys the recipe allowlist permits, nothing else) and restarts the desktop; Docker data in the desktop is untouched. Always allowed to Gateway because it only reduces exposure. Returns `{restarted}`. Rate: 6 per hour. The client must warn that open apps close.

### 6.10 `CreateSnapshot` / `ListSnapshots` / `DeleteSnapshot` (A)

Names are generated by privd: `hx-<kind>-<utc timestamp>-<4 hex>` with `kind` ∈ `manual` (Gateway or Admin), `preupdate` (privd, before an update), `backup` (Phase 2, privd only, tagged and removed by crash recovery).

- `CreateSnapshot` {`desktop_id`}: creates a `manual` snapshot with `Client::create_snapshot` (S3 measured 0.2–0.5 s). At most 3 `manual` snapshots; a fourth is `RESOURCE_EXHAUSTED`. Refused when pool free space is below 15% or 2 GiB. Rate: 6 per hour. Deadline 60 s.
- `ListSnapshots` {`desktop_id`} (R): the `hx-`-prefixed snapshots only, at most 64: `{name, kind, created, size}`.
- `DeleteSnapshot` {`desktop_id`, `name`} (A): `name` must match `^hx-(manual|preupdate|backup)-[0-9TZ-]+-[0-9a-f]{4}$` and exist. Gateway may delete `manual` only; Admin any `hx-` snapshot. A name outside the pattern is `INVALID_ARGUMENT`; privd never touches a snapshot it did not name. Idempotent (already gone succeeds).

### 6.11 `ProvisionSessionLink`, `InstallSession`, `RestartSession` (A)

**`ProvisionSessionLink`** {`desktop_id`}: ensures that the one Incus **proxy device** that exposes `hx-session` to gatewayd exists, with these properties (computed by privd, never given by a caller; the rationale and the alternatives are in §11):

| Property | Value |
|---|---|
| device name / `type` | `hx-link` / `proxy` |
| `bind` | `host` |
| `listen` | `unix:/run/hx/link/<desktop_id>.sock` |
| `connect` | `unix:/run/hx-session/link.sock`, a fixed path in a root-owned directory inside the container (§11) |
| `uid`, `gid`, `mode` (the host-side listening socket) | the gatewayd uid and gid, `0600` |
| `security.uid`, `security.gid` (the identity the container side connects as) | **mandatory**: the desktop user's uid and gid from the recipe (1000), not read from the container. There is no fallback: if the property does not behave as specified on a supported Incus, the design is reopened (§11), not weakened. |

It also ensures `/run/hx/link/` exists as root:`hx-gatewayd` 0750 (so gatewayd can traverse it but cannot create, rename or delete entries, and cannot substitute a socket). Converge; the device persists across restarts and is the only device privd ever adds to a desktop. Returns `{socket_path}`. Rate: 6 per hour. *Gap in hx-provision: the Incus client has no device-add call; §21.* Failure: if the container does not accept the device, `FAILED_PRECONDITION` with the Incus message sanitized.

**`InstallSession`** {`desktop_id`}: pushes the `hx-session` package for the desktop's distro from privd's own artifact store (`/usr/lib/hx/session/<distro>/`, minisign-verified with the agent release; the caller supplies no path, URL or bytes) into `/var/lib/hx/session/` in the container with `push_file`, installs it with a fixed `dpkg -i` exec (bounded output via `exec_captured`), and restarts the session with a fixed-argv exec as root inside the container: `systemctl reset-failed hx-session.socket hx-session.service`, then `systemctl restart hx-session.socket hx-session.service` (without the reset, systemd's start-rate limits can leave the socket in the failed state) (§11 explains why it is a system unit running as the desktop user). Converge (same version: no-op). Returns `{installed_version, restarted}`. Used at creation and after an agent update (architecture §5.5: "pushed into the container by the agent; only the streaming process restarts"). Rate: 6 per hour; deadline 5 minutes.

**`RestartSession`** {`desktop_id`}: runs the same fixed sequence (`reset-failed` for the socket and the service, then restart both) and nothing else; user applications keep running (architecture §6, S2 lesson: `hx-session` owns the processes it manages). gatewayd calls it after repeated link faults (§19.2). Rate: 6 per hour per desktop. *Note for 1D: if `hx-session` were ever run as a user unit, the container exec would have to run as the desktop user, and `hx_provision::ExecSpec` has no user field today; the system-unit design avoids that dependency.*

*Naming:* the streaming daemon is `hx-session.service`. The recipe unit that currently takes that name (`recipes/fragments/xfce-desktop.toml`, it runs `xfce4-session`) must be renamed, for example `hx-xsession.service`; a 1D/recipes follow-up (§21).

### 6.12 `CheckUpdate`, `ApplyUpdate`, `RollbackUpdate` (self-update hooks)

Network access is done by a sandboxed **update fetcher** that privd spawns on demand. **Contract-level rules for the fetcher** (sandbox details belong to 1C/1D): a dedicated dynamic user; no capabilities; `RestrictAddressFamilies=AF_INET AF_INET6` (**no `AF_UNIX`**, so it cannot reach privd's, Incus's or gatewayd's sockets); network access only to the release hosts; a 15 s connect timeout and a 10 minute overall timeout per artifact; a size quota (manifest at most 1 MiB, agent release at most 256 MiB, each `hx-session` package at most 64 MiB, a prebuilt image at most 4 GiB, whole staging directory at most 5 GiB, enforced with `LimitFSIZE` and a directory quota); it writes only to `/var/lib/hx/updates/`. Root privd never speaks HTTP.

**Rules privd follows for what the fetcher left** (the directory is hostile: the fetcher can be compromised, and can change files after they were checked):

1. **Strict version string first.** A version is `^[0-9]{1,4}\.[0-9]{1,4}\.[0-9]{1,4}(-(alpha|beta|rc)\.[0-9]{1,4})?$`; anything else is rejected before the string is used in any path, command or log.
2. **Read once, verify what you use.** privd opens the artifact once, through a directory fd opened `O_DIRECTORY|O_NOFOLLOW` and `openat2` with `RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS`, requires a regular file with link count 1 and size within quota, and copies it from that fd into memory (small files) or into an `O_TMPFILE` in the root-only `/var/lib/hx/staging/`. Minisign and SHA-256 are verified over **exactly those bytes**, and only that copy is used afterwards; the fetcher's file is never reopened.
3. **Manifest freshness.** The signed manifest carries a timestamp; privd persists the highest accepted value in `/var/lib/hx/updates-state` and rejects an older manifest (so a replayed old, signed, vulnerable release is refused), in addition to the rule that a version must be newer than the running one.
4. **Safe extraction** (done by privd, in process, from the verified copy, with `openat2(RESOLVE_BENEATH)` under a root-owned `/usr/lib/hx/<version>/`): refuse absolute paths, any `..` component, names with NUL, duplicate entries, symlinks and hard links whose target leaves the extraction root, device nodes, fifos and sockets, and setuid, setgid and sticky bits (modes are masked); at most 4 096 entries and 1 GiB uncompressed in total.

- **`CheckUpdate`** (class A, both) {}: the channel (`stable` or `beta`) comes from `privd.toml`, not the request. Spawns the fetcher, then verifies the signed release manifest as above. Returns `{current, available (optional), channel, verified: true, rolled_back (optional: version and reason; see the health check below)}`. Deadline 60 s; rate 6 per hour.
- **`ApplyUpdate`** (A, both) {`version`}: `version` MUST equal a release privd has already fetched and verified by the rules above: minisign signature valid against the **embedded current or next key** (installer rule, architecture §13), SHA-256 matches, `version` strictly newer than the running one (**no downgrade by request**), built for this arch. privd takes a `preupdate` snapshot of the desktop (best effort), unpacks to `/usr/lib/hx/<version>/`, flips `/usr/lib/hx/current` atomically, restarts gatewayd and then re-execs itself, answering the request first with `restarting`. After a successful agent update gatewayd calls `InstallSession`.
- **Health check and rollback.** The update counts as healthy when, within 90 s: (1) privd answers on its socket after re-exec; (2) the gatewayd process is up (systemd reports it active with a stable `MainPID` for 30 s); and (3) gatewayd's **admin socket** answers `Status` (§9). The admin socket is used because it sits outside the pre-authentication connection limits, so an internet flood that fills the public listener cannot cause a rollback. A failed check flips the symlink back, restarts, and records `needs_attention=UPDATE_ROLLED_BACK` with the reason. **The session-link handshake and a loopback `Hello` are reported in `Status` but are never rollback criteria** (an unreachable container or a full pre-auth table is not evidence that the new binaries are bad). After a rollback privd keeps **re-offering** the same update (`CheckUpdate` still returns it as available, with `rolled_back` set, and status shows the flag); it is never re-applied automatically, only by a new `ApplyUpdate`.
- Rate: `ApplyUpdate` 2 per day; deadline 10 minutes; progress stage `UPDATE`.
- **`RollbackUpdate`** (X, Admin) {}: flips back to the previous retained version (two are kept). The signature rules still apply because the old files were verified when installed.

### 6.13 Admin-only commands (class X)

- **`DestroyDesktop`** {`desktop_id`, `confirm_destroy` true}: stops and deletes the instance (`destroy_instance`) and its `hx-` snapshots, removes the proxy device. Used by repair and by Phase 2 restore, and by `Uninstall`. Idempotent.
- **`Uninstall`** {`keep_desktop` bool, `confirm_destroy` bool (required true when `keep_desktop` is false)}. Idempotent and resumable (state kept in `/var/lib/hx/uninstall-state` until done; "every stage is idempotent", architecture §5.3). `keep_desktop=true`: removes the agent (units, sockets, binaries, `/etc/hx/creds`, registry, the link proxy device) but **leaves the desktop, pool, bridge, ACL, profiles, the host firewall unit and the sysctl file**, because removing the firewall would silently weaken a desktop that keeps running; the CLI says how to remove them later. `keep_desktop=false`: additionally destroys the desktop and its snapshots, then deletes the profiles, ACL, bridge and pool, the nftables table and unit, the `DOCKER-USER` rules and unit, and the sysctl file. It deletes only objects named by `Naming::production()` **and** carrying the hash-xcreen marker, never an object that merely has a matching name pattern, and never uninstalls Incus itself. **Deletion is symlink-safe** (§7, rule 15): everything under a directory that gatewayd can write (`/var/lib/hx-gatewayd`, its runtime directory) is removed with `unlinkat` relative to a directory fd opened `O_NOFOLLOW`, never by path and never recursively through links, and a mount point or symlink found in the tree is removed as an entry and not followed.
- **`ResetLockout`** {`purpose` ∈ `PIN`, `PASSWORD`}: Admin only; clears the failure counters and the `PIN_LOCKED`/`PASSWORD_LOCKED` flag of §5.3 and records the event.
- **`EnrolOwnerKey`** {`public_key` 32 bytes} (Phase 2 shape; accepted but unused in Phase 1): records the owner public key (§5.2). Admin only, so the key is enrolled outside gatewayd's control (by the installer over SSH, or `hx-agent owner enrol`). Replacing an enrolled key requires `replace: true`.
- **`UpgradeIncus`**: installs a newer Incus from the Zabbly repository (Docker fallback 1). Admin only because it changes host packages; **reserved in Phase 1** (`UNIMPLEMENTED`), the CLI documents the manual step.

### 6.14 Reserved for Phase 2 (named, not specified)

`BackupRun`, `BackupCancel`, `BackupStatus`, `ListBackups`, `SetBackupSchedule`, `SetBackupCredentials`, `VerifyBackup`, `PruneBackups`, `RestoreStart`, `RestoreStatus`, `RestoreConfirm`, `GenerateRecoveryKey`, and `BeginSecretUpload` {`kind`, `desktop_id`} (class A, returns the one-time `upload_nonce` of §5.2; also `UNIMPLEMENTED` until the first sealed secret exists). In Phase 1 every one answers `UNIMPLEMENTED`. Constraints they must meet (so this contract does not need a breaking change):

- Gateway may request, observe and cancel; it never supplies a path, snapshot name, repository location or credential in the clear. `SetBackupCredentials` takes `DRIVE_TOKEN`/`BACKUP_KEY` **sealed only, owner-authenticated, with a privd-issued nonce** (§5.2).
- privd takes the snapshot, attaches it read-only to the worker with the idmapped mount (architecture §9.4 step 2) and spawns the sandboxed worker; the worker never holds the Google credential, only a repository handle from privd.
- The recovery key is generated by privd/the worker and delivered to the client **sealed to the device key**, not as plaintext through gatewayd, since "shown once" must not mean "seen by gatewayd".
- `RestoreStart` restores through Incus (isolated idmaps, architecture §9.8 item 7), into a temporary instance, never replacing the live desktop before the boot check passes.
- A `backup` snapshot is always tagged so crash recovery can delete leftovers (architecture §9.6).

### 6.15 `PepperVerify`, `PepperEnrol` and `RecordEvent` (class A, Gateway and Admin)

**`PepperVerify`** {`purpose` ∈ `PIN`, `PASSWORD`; secret slot 0 `MAC_INPUT` (32 bytes, the Argon2id output); `expected_verifier` (32 bytes, the stored value)}: computes `HMAC-SHA256(HKDF(pepper, purpose), input)` and compares it with `expected_verifier` in constant time; returns **only** `{ok: bool}` (never the MAC, never the pepper version of a failing verifier). Failures are counted per purpose **globally** (not per caller or device) with the caps and the lock of §5.3, persisted (§8); successes are free. A locked purpose answers `RESOURCE_EXHAUSTED` (`LOCKED`) to every call. Audit log: purpose, ok or fail, never the input. Shielded against cancellation (§4).

**`PepperEnrol`** {`purpose`; secret slot 0 `MAC_INPUT`}: returns `{mac (32 bytes), version (u8)}`; nothing is stored. Used only to set or change a verifier (client sets a PIN, `SetUserPassword` succeeded, the SSH installer, `hx-agent`). Gateway: at most **5 per day** after setup and 60 per hour during `SETUP_OPEN`; Admin is exempt. Counted globally, persisted, audited; shielded.

**`RecordEvent`** {`event` ∈ `DEVICE_ADDED`, `DEVICE_REVOKED`, `DEVICE_REINSTATED`, `PIN_CHANGED`, `PASSWORD_VERIFIER_CHANGED`, `PAIRING_OPENED`, `TAKEOVER`; `device_id` (16 bytes, optional); `label` (at most 64 bytes, sanitized and logged only)}: writes the event to privd's audit log (§8), which is how registry changes become visible in a log gatewayd cannot edit. Best effort and rate limited (60 per hour); it grants gatewayd nothing. A compromised gatewayd can omit or forge these events, so the audit log is evidence for honest operation and a tripwire for noisy attacks, not a guarantee.

## 7. What privd refuses (confused-deputy rules)

privd is the deputy; gatewayd is the less-privileged caller. These hold regardless of what a request says:

1. **No caller-chosen names.** Instance, snapshot (other than the generated kinds), pool, network, ACL, profile and device names, `Naming`, `HostSpec`, `PoolSource` (except `LoopFile` size), `Catalog` roots and `DockerOptions::allow_old_incus` are never taken from a Gateway request. They are constants or derived by privd.
2. **No caller-chosen paths or addresses.** No host path, image URL or server, release URL, socket path, mount source or proxy `connect`/`listen` value. In particular the proxy device's host path is computed, because a proxy device whose `connect` pointed at `/run/hx/privd.sock` or `/var/lib/incus/unix.socket` would hand the container the keys to the host.
3. **No arbitrary execution.** No command takes a command line, shell string, environment, recipe text, `incus_config` key or file content. Every `exec` (host: `nft`, `sysctl`, `iptables`, `dpkg`, `systemctl`; container: `chpasswd`, a shadow-hash check, `dpkg`, `systemctl restart hx-session.service`) is a fixed argv from constants, run without a shell, with a cleared environment, a timeout and a 64 KiB output cap.
4. **No Incus passthrough.** privd exposes no generic Incus REST call, device, profile or config edit. The only instance config keys it ever writes are the fixed set in `DesktopSpec::to_create`, the three Docker keys, `limits.cpu`/`limits.memory`, and `user.hx.*`.
5. **Privileged options stay with `Admin`.** `pool_device`, `allow_private_networks`, `extra_host_addresses`, `ipv4`, `image_file`, `UpgradeIncus`, `Uninstall`, `DestroyDesktop`, `RollbackUpdate`, `BeginSetup`, `ExtendSetup`, `EnrolOwnerKey`, and a `FinishSetup` with `force`. **`EnableDocker` is open to Gateway only while the setup window is open** (the wizard's `--docker` path); after setup it is Admin-only (`hx-agent docker enable`), because it lowers container isolation. `DisableDocker`, which only reduces exposure, stays open to Gateway.
6. **Setup commands only in the window.** `SetupHost` and `CreateDesktop` from Gateway outside `SETUP_OPEN` are `FAILED_PRECONDITION`.
7. **Caps.** Not more than the configured number of desktops (1), limits above host bounds, unlimited `limits.processes`, more than 3 manual snapshots, a disk below current use.
8. **Only objects we own.** Destructive commands act only on objects whose names match our naming and which carry our marker (`user.hx.*` for instances, the hash-xcreen description for pool, network, ACL and profiles). Snapshots not matching the `hx-` pattern are never listed, created over or deleted.
9. **Secrets only as declared.** A secret of the wrong `kind`, a plain `DRIVE_TOKEN` or `BACKUP_KEY`, a secret outside a declared slot, or a secret in a protobuf field, is `INVALID_ARGUMENT`.
10. **Updates only forward and signed.** An unsigned artifact, a signature from a non-embedded key, a version not newer than the running one, or a version privd did not itself fetch and verify, is refused.
11. **Isolation first.** While `needs_attention` holds `ISOLATION_NOT_RESTORED`, Gateway cannot start the desktop.
12. **Container-originated data is never interpreted.** Output from the desktop is sanitized and truncated, is never used as a path, command, URL or Incus parameter, and is never read through host paths into the container filesystem (architecture §8.5): files in the container are accessed only through the Incus API, and `record-output` is never used.
13. **No descriptors, no ambient trust.** No file descriptors over the socket (§3); no authorization from the pid, the executable path or any message field.
14. **No new concurrency channels.** A command that is rate limited or locked out does not queue indefinitely (§8).
15. **No paths inside a directory gatewayd can write.** privd and every root tool (`hx-agent`, the installer, the uninstall path) never open, create, delete, execute, parse or `chown` a path that lies inside a directory writable by the `hx-gatewayd` uid or by the fetcher uid (`/var/lib/hx-gatewayd`, its runtime and credential directories, `/var/lib/hx/updates/`, anything else gatewayd owns), because gatewayd could have planted a symlink, a hard link, a mount or a swapped component there. Where root must touch such data it does one of: (a) **drop to the owner's uid first** (`setresuid` to the gatewayd uid, for example for the offline registry edits of §9) so the kernel's permission checks are those of the less-privileged user; (b) if (a) is impossible, use `openat2(RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS)` against a directory fd opened `O_DIRECTORY|O_NOFOLLOW`, create files with `O_EXCL` as a temporary name and `renameat` within that directory fd, and never follow a path string a second time. Uninstall deletion is symlink-safe in the same way (§6.13). **Implementation note for (a):** `setresuid` happens in a **forked child** after `setgroups([])` (and `setresgid`), the child does only the file work and exits when done, and the parent never changes its own credentials. The same applies to root *reading* gatewayd state, such as ACME files (the credentials flow the other way, through `LoadCredentialEncrypted`, so root never reads them from gatewayd's tree).

# Part 2: the session link

## 10. Purpose, topology and trust

`hx-gatewayd` relays media and input between a client (protocol.md) and `hx-session`, the process inside the desktop container that captures, encodes and injects. The session link is the unix-socket connection between the two. It carries:

- encoded video frames with what the gateway needs to build the media header (§15), and the cursor (§14);
- input events from the client, including a coalesced mouse-motion stream (§14);
- clipboard and file transfers in both directions (§16);
- per-frame delivery feedback and cancel signals from the gateway to the session's congestion controller, and cancel requests the other way (§14, §15);
- control: start and stop streaming, reconfigure (bitrate cap, frame rate, resize to the client window, policies), request an IDR, statistics, goodbye (§14);
- audio, reserved (§15.4).

**Trust.** `hx-session` runs as the desktop user in a container whose software the user controls and which may be compromised; malware there has the same uid as `hx-session`. Everything arriving on the link is **untrusted input** to the internet-facing gatewayd, parsed with explicit limits before allocation (§13, §19). Nothing secret ever goes over the link: no PIN, device key, token, password, client address or device name. The gateway sends only what the desktop needs to render and act: input, display and policy settings, feedback counters.

What malware in the container can do with the link, and why that is acceptable:

| Action | Result |
|---|---|
| Replace or impersonate `hx-session` (listen on the socket path first, or kill it) | It can show the client any picture and cursor, send any clipboard, and observe the input sent to the desktop. All of that is already within its power (it controls the screen and receives the keystrokes anyway); the client treats remote clipboard and links as untrusted (architecture §8.7). |
| Send malformed or oversized data, or flood | Bounded by the §13 limits, the §19 validation and rate limits; a violation drops the link and does not affect gatewayd's other duties. |
| Send decodable-but-malicious video or cursor data | Reaches the client's decoder. Two layers: gatewayd checks the Annex B structure and the SPS dimensions of key frames (§15.1), and the client decodes in a sandbox with a `max_pixels` limit and is fuzzed (1G/1H; §22, decision 8). |
| Reach anything else through the socket | Nothing: the socket is a byte pipe to one gatewayd connection (§11); there is no descriptor passing, and the link carries no authority (no secrets, no path to privd). |

## 11. Transport and socket placement

**Decision: an Incus proxy device, with gatewayd dialling out and `hx-session` listening on a systemd-created socket in a root-owned directory.**

```
 host                                                     container (unprivileged, isolated idmap)
 hx-gatewayd ──connect──► /run/hx/link/main.sock  ⇄ forkproxy ⇄ /run/hx-session/link.sock ◄── hx-session.socket (systemd)
   (uid hx-gatewayd)       (listening socket made by the          (dir root:root 0755; socket owned by the desktop
                            proxy device, owner hx-gatewayd 0600)  uid, 0600)           └─ fd handed to hx-session.service
```

- **Container side**: a fixed path, `/run/hx-session/link.sock`, in a directory that is **root-owned (0755)**, so the desktop user, and therefore malware running as it, can neither rename, delete nor replace the socket path, nor swap the directory for a symlink. The socket is created by a systemd **socket unit** inside the container (`hx-session.socket`: `ListenStream=/run/hx-session/link.sock`, `SocketUser=<desktop uid>`, `SocketGroup=<desktop gid>`, `SocketMode=0600`, `DirectoryMode=0755`, `Accept=no`) and handed to `hx-session.service` (a system unit with `User=<desktop uid>`, which reads the descriptor with `sd_listen_fds`; a system unit is required because only system socket units support `SocketUser=`, and it also means no `loginctl enable-linger` is needed for the daemon). **`hx-session` must never launch user-facing programs.** The unit has `KillMode=control-group`, so anything it starts dies with it, and it runs outside the user's login session; if the daemon ever has to start an application it uses `systemd-run --user` or asks the X session, never `fork`/`exec` of its own. A side benefit: systemd holds the socket while `hx-session` restarts, so connections queue instead of failing, and the service starts on the first connection. No other account in the container can connect (root in the container can; root there is part of the container's trust domain).
- **Host side**: `hx-privd` adds one proxy device per desktop (`ProvisionSessionLink`, §6.11): `bind=host`, `listen=unix:/run/hx/link/<desktop_id>.sock`, `connect=unix:/run/hx-session/link.sock`, host-side socket owned by the gatewayd uid and gid, mode `0600`, **`security.uid` and `security.gid` set to the desktop user's ids (mandatory)**, so the container-side connect runs as that user and not as the container's root. **Both are required**: with only `security.uid` the connect arrives as gid 0, and with neither it arrives as uid 0 (spike 1C controls). A stopped container or a removed device leaves a stale socket file on the host whose connect is refused (`ECONNREFUSED`), and a connect that the proxy cannot complete on the container side is reset right after it is accepted, so gatewayd treats both as "session not available" and redials (§19.2). `/run/hx/link/` is root:`hx-gatewayd` 0750, so gatewayd can connect but cannot create, rename, replace or delete entries; no other host user can reach it.
- **No fallback to the container's root.** If `security.uid`/`security.gid` do not behave as specified on a supported Incus version, implementation stops and the design is reopened. Falling back to a root-identity connect would make the forkproxy a root-in-container actor that follows whatever the container presents at the path, and is rejected.
- **Direction**: gatewayd connects when it needs the desktop (first authorized client) and `hx-session` accepts. Reasons: (1) the gateway fully controls how many connections exist, which keeps its attack surface at a fixed number of connections per desktop instead of an accept loop that malware can hammer; (2) a gatewayd restart needs no cleanup in the container; (3) `hx-session` idles at about zero cost with no link, and streams only while one exists.
- **Why a proxy device, not a shared directory or a socket bind-mounted from the host.** The proxy copies bytes between two sockets it owns, so the container never obtains a kernel-level handle to a host-created socket: no `SCM_RIGHTS` descriptor passing into gatewayd, no peer-credential games, no dependency on how the isolated idmap shows host owners. A bind-mounted directory would also give the container a path on the host filesystem.
- **Peer identity.** There is none to authenticate on the container side: `SO_PEERCRED` of an accepted connection shows the proxy process, not the gateway, and anything running as the desktop user could connect too, which gives it nothing beyond what it already has (§10). gatewayd does not authenticate `hx-session` either: the host socket path proves "this is the proxy device privd created for this desktop", and the handshake (§12) proves nothing beyond the protocol version. Neither side's decisions rely on the identity of the other. gatewayd reads the link with `recvmsg` and treats any control message or `MSG_CTRUNC` as a violation (the same rule as privd's, §3).
- **Verified first in 1C implementation, on real Incus 6.0.0 with an isolated idmap** (decision 10, §22; evidence in [spikes/1c-proxy-device.md](spikes/1c-proxy-device.md): all four items hold). Not yet run, to repeat on the first real VPS: the host reboot and Incus daemon restart of item 2, and the unprivileged-user-namespace variant of item 4 (the spike host's `kernel.apparmor_restrict_unprivileged_userns=1` forbids creating one). The checklist stays as the regression list: (1) `uid`, `gid`, `mode` of the host-side socket and `security.uid`/`security.gid` of the connect side behave as above; (2) connections work after the container is stopped and started and after a host reboot; (3) throughput at 20 Mbps with frames up to the configured cap; (4) **the symlink and replacement test**: as the desktop user inside the container, attempt to unlink, rename or replace `/run/hx-session/link.sock` and `/run/hx-session`, to place a symlink at the path or in front of it, to bind a different listener at the path while the socket unit runs, and to bind-mount over it (unprivileged user namespaces inside the container included); every attempt must either fail or leave the proxy connecting only to the systemd-created socket as the desktop user, and the test must also confirm that nothing the container does makes the proxy connect to a host path.
- **Rejected alternatives**: a TCP port on the bridge (the bridge's nftables rules and ACL deliberately forbid desktop-to-host traffic; opening a hole for this would weaken the isolation both layers exist to provide); `/dev/incus` or the guest API (`security.guestapi=false` on every desktop); vsock (containers have none; only VMs); a socket in the desktop user's `XDG_RUNTIME_DIR` (the user controls that path, the original v0.1 placement).

## 12. Connection lifecycle

### 12.1 Lanes

One link is **three** unix connections (lanes) to the same socket path, so that large or slow data never blocks small urgent data. Each lane is a separate byte stream through the proxy.

| Lane | Id | Direction of bulk traffic | Carries |
|---|---|---|---|
| `ctl` | 1 | both, small messages | handshake, control, input, mouse motion, cursor, frame feedback, cancels, statistics, events |
| `media` | 2 | session → gateway | video frames, audio (reserved) |
| `bulk` | 3 | both | clipboard and file transfers |

The gateway to session direction of `media` is unused; a byte received there is a violation.

### 12.2 Preamble and versioning

Each lane starts with an 8-byte preamble from the connecting side (the gateway), followed by a 16-byte `link_id` (random, chosen by the gateway per link, identical on the three lanes). The session answers with the same 8 bytes:

```
 0       4        5        6      7
+--------+--------+--------+------+------+----------------+
| "HXLK" | major  | minor  | lane | 0x00 | link_id (16 B) |   gateway → session
+--------+--------+--------+------+------+----------------+
```

The answer has the first 8 bytes only, with `minor` lowered to the session's if that is lower. Rules:

- The link version is `1.0`. Same major, different minor is accepted; the negotiated minor is the lower one, and a newer minor never sends a message to a peer whose negotiated minor predates it (the rule of protocol.md §4.2). A different major is refused by closing the connection; gatewayd then records `session_outdated` for the desktop and asks privd for `InstallSession` (an update replaced the agent but not the in-container binary).
- `hx-session` accepts at most **one link** (one `link_id`) at a time with at most one connection per lane. A new `link_id` on a `ctl` lane **supersedes** the old link: the old lanes are closed and the session behaves as for link loss (§12.4). A duplicate lane of the current link is closed.
- The gateway opens `ctl` first and waits for the session's `info` (§14.2); it opens `media` and `bulk` after that. If the session does not see both extra lanes within 5 s of `ctl` it drops the link. Preamble and `info` must complete within 5 s of connect, else the gateway closes.
- A malformed preamble, wrong magic, a `lane` outside 1 to 3 or a non-zero reserved byte closes the connection (on the gateway: a violation, §19.2).

### 12.3 Liveness

- The gateway sends `ping` {`nonce`} on `ctl` every 2 s while a link exists; the session answers `pong` within 1 s from its control thread (never from the media path). 10 s without a `pong` and no other `ctl` traffic: the gateway closes the link (a fault, §19.2).
- While streaming, the session also sends `stats` about once per second, which doubles as a heartbeat. An idle desktop produces no frames by design (architecture §6.1), so frame silence is not a liveness signal.
- The session closes the link and stops streaming if it receives nothing from the gateway for 15 s.

### 12.4 Link loss and restart

When the link closes for any reason the session, within 1 s: stops capture and encoding (idle cost about zero), injects **`release_all`** (every held key and button up), aborts transfers, discards queued output, and returns to listening for a new link. It never exits because the link ended. The gateway treats a lost link while a client is connected as `INTERNAL_ERROR`: it sends the client `Goodbye`, then redials with backoff, and the client reconnects to a fresh stream (video restarts from an IDR regardless).

## 13. Framing and limits

After the preamble every lane carries frames:

```
+----------------+---------+------------------------+
| length (u32 LE)| kind u8 | body (length - 1 bytes)|
+----------------+---------+------------------------+
```

The same shape as §4, so one reader implementation serves privd and the link. `length` counts the kind byte and body and is checked against the table **before** allocating. An unknown `kind`, a `kind` not valid on that lane or in that direction, a zero or oversize `length`, a frame truncated by a close, or a protobuf body that fails to decode is a **violation** (§19.2). An unknown *protobuf variant or field* inside a valid message is ignored and counted (forward compatibility).

| Lane | Kind | Direction | Body | Max `length` |
|---|---|---|---|---|
| `ctl` | `0x01` `SessionToGateway` | S → G | protobuf (§14) | 327 685 (the 327 680-byte cursor limit of protocol.md §3.1: a 256 × 256 RGBA shape is 262 144 bytes plus protobuf overhead; plus the kind byte) |
| `ctl` | `0x02` `GatewayToSession` | G → S | protobuf (§14) | 16 384 |
| `media` | `0x10` Video | S → G | media header (20) + payload (§15) | `max_frame_bytes` + 21: 4 194 325 by default (4 MiB), configurable up to the protocol's 16 777 237 (16 MiB) |
| `media` | `0x11` Audio | S → G | `seq` u32, `timestamp` u32, Opus packet 1 to 1 100 | 1 110 (reserved, §15.4) |
| `bulk` | `0x20` TransferOpen | both | protobuf `TransferOpen` {`id` u32, `channel` (CLIPBOARD or FILE), `header` = protocol `TransferHeader`} | 4 200 |
| `bulk` | `0x21` TransferData | both | `id` u32 + raw bytes (1 to 65 536) | 65 541 |
| `bulk` | `0x22` TransferEnd | both | `id` u32 | 5 |
| `bulk` | `0x23` TransferAbort | both | `id` u32 + `code` u32 (protocol.md §8 transfer codes) | 9 |

Message-level limits (checked by the **gateway** for S → G and by the session for G → S):

Repeated fields are **counted on the wire before the message is decoded** (`info.codecs` at most 4, `frame_feedback.results` at most 64), so a 327 685-byte `ctl` body of empty elements cannot make the decoder allocate ten times its size; the remaining allocation per frame is bounded by the frame limit itself and measured in `hx-ipc` `tests/alloc.rs`.

| Item | Limit |
|---|---|
| Strings (`software`, event `message`, `goodbye` `message`) | 128, 256, 256 bytes; control and ANSI characters removed before display or logging |
| `stats` | 4 per second; every counter a bounded integer |
| Cursor shape | at most 256 × 256, `rgba.len == width * height * 4`, hotspot inside the image (protocol.md §5.4); at most 20 shapes per second and 4 MiB of shape data per second |
| Cursor position | coalesced by the gateway to at most one per 1 ms (latest wins); never queued unboundedly |
| `event` | 10 per second |
| Video frame payload | at most `max_frame_bytes` (default 4 MiB, configurable up to the protocol's 16 MiB; deliberately below the protocol limit, because the link carries one frame at a time from a hostile source and an IDR at 20 Mbps is far smaller; the session's encoder must stay under it); at most 2 × the negotiated `max_fps` frames in any one-second window; at most 4 IDR frames per second |
| Transfers | at most 4 concurrent per direction; one clipboard transfer per direction at a time (a new one aborts the previous); clipboard at most 64 MiB; file at most `max_file_bytes` (default 4 GiB, configurable lower, enforced in both directions; the protocol follow-up of §21 puts it in protocol.md); chunks at most 64 KiB; unread data at most 1 MiB per transfer and 4 MiB per link |
| Input G → S | `InputEvent` at most 1 024 (protocol.md §3.1); input queue 4 096 events |
| Memory per link on the gateway | video pool of `max(2 × max_frame_bytes, 12 MiB)` (**always at least one maximum-size frame, in fact two**), plus at most 8 MiB for `ctl` and `bulk` buffers: 20 MiB at the default cap, 40 MiB at the 16 MiB ceiling |
| `stream_format` | at most 4 per second; `width` and `height` each 1 to 16 384, `width * height` at most 33 177 600 (7680 × 4320); `fps` 1 to 240; `codec` in the negotiated set; `first_frame` within 8 behind and 1 024 ahead of the newest frame number received (serial arithmetic); an out-of-range value drops the message and is counted |
| `cancel_frames` | at most 8 per second; `up_to_frame` must not be newer than the newest frame number the gateway has received and not more than 256 behind it; otherwise ignored and counted |
| `info` | accepted once per link, as the first `ctl` message; `display` 1 to 16 384 per side; `features` unknown bits ignored; a second `info` is a violation |
| `pong` | a `pong` with a nonce the gateway did not send, or a second one for the same `ping`, is ignored and counted; more than 10 per second is a violation |
| Byte budget per lane (sustained, burst = 2 s) | `ctl` S → G 6 MiB/s (shapes 4 MiB/s of it), `ctl` G → S 1 MiB/s, `media` S → G 16 MiB/s with an IDR burst allowance of `max_frame_bytes`, `bulk` 64 MiB/s per direction. **Beyond the budget the gateway stops reading that lane** (the kernel buffers fill and the session's writes block: backpressure) instead of reading and discarding it. A lane whose bucket stays empty for 3 consecutive seconds because the session keeps sending at full speed is a violation (§19.2); a pause caused by downstream flow control (a slow client) is not. |
| Frame count per lane (bytes do not bound per-frame CPU) | Per second, all kinds together: `ctl` S → G 2 000 (cursor positions at most 1 000 plus about 50 of the capped classes, with headroom), `ctl` G → S 4 000 (input 2 000, motion 1 000, feedback and stats), `bulk` 2 048 per direction (a 64 MiB/s transfer is 1 024 chunks of 64 KiB), `media` audio 200 (reserved; 100 per second plus headroom). `ctl` frames that decode to no known variant: at most 10 per second (a negotiated peer sends none). **Exceeding any of these is a violation** (§19.2), unlike the message-class limits above, where only the excess is dropped. Values are `hx_ipc::link::budget::limits`. |

## 14. Control lane (`ctl`)

Messages are protobuf. They reuse the `hx.v1` types of protocol.md wherever the content is the same (`InputEvent`, `CursorEvent`, `ClientStats`, `TransferHeader`, `VideoCodec`), so field semantics are not defined twice. The new messages below belong to a package `hx.link.v1` (schema location: decision 9, §22).

### 14.1 Gateway to session: `GatewayToSession` (`oneof`)

| Variant | Fields | Meaning |
|---|---|---|
| `start` | `epoch` u32, `config` (`StreamConfig`) | Begin streaming for a client. The session creates or resumes the pipeline, replies `stream_format`, and its first frame is an IDR flagged `RESYNC`. `epoch` identifies the client (§18); the controller resets on `start`. |
| `stop` | `epoch` | Stop capturing and encoding within 1 s (the last client left). Keeps listening; clears held keys. |
| `reconfigure` | `config` (`StreamConfig`) | Apply new settings while streaming (client window resize, bitrate cap, frame rate, policies). Zero (unset) fields keep their value, as `ViewConfig` does. |
| `request_idr` | `epoch`, `last_decoded_frame` u32 | The client lost sync (protocol `RequestKeyframe`) or the gateway dropped frames. The session's next frame is an IDR flagged `RESYNC`. The gateway sends at most 2 per second; the session coalesces repeats. |
| `input` | `event` (`hx.v1.InputEvent`) | One validated key, button, scroll or `release_all` event, in client order. |
| `mouse` | `seq` u32, `relative` bool, `x` sint32, `y` sint32 | Latest-wins pointer motion, already coalesced by the gateway (§17). Absolute values are clamped to the current display; relative deltas to ±32 768. |

| `client_stats` | `hx.v1.ClientStats` | Forwarded client decode statistics (about 1 per second). |
| `ping` / `goodbye` | `nonce` u64 / `code` u32, `message` | Liveness; orderly end. `code` is a protocol.md §8 close code. |

`StreamConfig`:

| Field | Type | Validation (gateway before sending; session again on receipt) | Meaning |
|---|---|---|---|
| `codec` | `VideoCodec` | `H264` in v1; anything else is ignored and answered with `event` `CAPTURE_ERROR` | Codec to produce |
| `max_fps` | u32 | 0 (keep or default) or 1 to 240 | Frame ceiling (`Control::set_max_fps`, 60 in v1) |

| `width`, `height` | u32 | both 0 (keep) or each 1 to 16 384; the session rounds down to even | Desired remote size from the client window (`Control::request_resize`) |
| `scale_percent` | u32 | 0 (= 100) or 50 to 400 | HiDPI scale |
| `audio_enabled` | bool | requires the `AUDIO` feature | Reserved |

| `file_transfer_enabled` | bool | | When false the session refuses file transfers |

| Variant | Fields | Meaning |
|---|---|---|

| `stream_format` | `epoch`, `codec`, `width`, `height`, `fps`, `first_frame` u32 | The format from `first_frame` on (becomes the client's `StreamInfo`, protocol.md §5.2). | `cursor` | `event` (`hx.v1.CursorEvent`) | Shape (RGBA, straight alpha, content-hash `id`) or position. | `event` | `kind` (`FATAL`, `DISPLAY_CHANGED`, `CAPTURE_ERROR`, `CLIPBOARD_ERROR`, `RESIZE_REFUSED`), `message` (at most 256) | Something the gateway should log or tell the client. `FATAL` means the pipeline stopped (`Control::fatal_error`). |

## 15. Media lane (`media`)

### 15.1 Video frame

One `kind 0x10` frame per encoded frame. The body is **exactly** protocol.md §6's 20-byte media header followed by the encoded payload, so the gateway validates the header and then forwards header and payload unchanged as the body of the client's frame stream (channel byte `0x05` first on QUIC; the identical bytes inside a `0x05` message on WebSocket). That keeps the path zero-copy friendly: the gateway reads each frame into one pooled buffer (`bytes::Bytes`) and slices it; it never re-encodes or concatenates.

How the session fills the header:

| Header field | Source |
|---|---|
| `version` | `1` |
| `codec` | `EncodedFrame.codec` mapped to the `VideoCodec` number (H.264 = 1) |
| `flags` | bit 0 `KEY` = `EncodedFrame.idr` (an IDR; a gradual-intra-refresh recovery point does **not** set `KEY`, because `KEY` means "decodes without earlier frames"); bit 1 `RESYNC` = this IDR answers a `start`, a `request_idr`, a `cancel_frames` or a gateway cancel. Other bits 0. |
| `frame_number` | a `u32` counter owned by the link layer, incremented for **every** `EncodedFrame` taken from `Pipeline::frames`, including one dropped before it is written, so a gap means "skipped". It does not follow `EncodedFrame::frame_no` (a `u64` that restarts when the encoder is recreated). Wraps modulo 2^32. |
| `capture_timestamp_us` | the frame's capture time on the container's monotonic clock in microseconds (from `EncodedFrame.timing`, `hx_capture::mono_ns` / 1000); the client only uses differences |
| `payload_len` | `EncodedFrame::bytes().len()` |

Width, height and fps are **not** in the header; they travel in `stream_format` (§14.2).

Gateway validation per frame, before the payload is accepted: `length` within the limit; header present; `version == 1`; `codec` equals the negotiated codec; no reserved flag bits; `payload_len == length - 21`; `frame_number` strictly newer (serial arithmetic) than the last accepted on this link, else drop and count; rate limits of §13; and a bounded **bitstream sanity check** (decision 8, §22): the payload begins with an Annex B start code; scanning at most its first 64 KiB, every NAL header has `forbidden_zero_bit` 0 and a valid type; on a `KEY` frame an SPS (type 7) is present and parsed with a small exp-Golomb reader (no allocation, `forbid(unsafe_code)`) and its coded size, after cropping, equals the `stream_format` in force for that frame and does not exceed the 7680 × 4320 pixel cap. A structural or sanity failure is a link violation (§19.2); a rate overage drops the frame. The gateway does **not** decode the payload and does not alter the header (which is why the header is validated, not rewritten). The client defends itself independently (sandboxed decode with a `max_pixels` limit, fuzzed; 1G/1H).

### 15.2 Backpressure and no unbounded queues

- The gateway **always drains the media lane**: it reads each frame promptly into the video pool of §13 (never smaller than one maximum-size frame). It drains the lane at the speed the session sends it, within the lane's byte budget (§13), and never because of a slow client: a slow client leads to cancels and drops at the gateway (below), not to a paused lane, so the session's writer never blocks behind it and `Pipeline::frames` is never stalled by the network. Only the byte budget can pause reading.
- Toward the client, the gateway limits frames in flight to what the transport window allows. When a frame cannot be sent within the window or a budget of about 100 ms, it is **not queued**: the oldest not-yet-delivered frame streams are reset with `STALE_FRAME` (protocol.md §6.2) and reported as `CANCELLED`, and frames never started are reported as `DROPPED`.
- Because H.264 P-frames depend on earlier frames, any cancel or drop breaks the chain. After one, the gateway discards every frame that is not `KEY` until the next `KEY | RESYNC` frame and sends `request_idr` (limited to 2 per second). This is the "cancel queued frame streams and send a fresh full image" rule of architecture §7.4, with the gateway doing the stream resets and the session producing the fresh image.
- The session's own writer must complete each frame it starts (a half-written frame would desynchronise the lane). A write that makes no progress for 2 s closes the lane (a fault).

### 15.3 Acks and cancels (feedback to the congestion controller)

`frame_feedback.results`: one `FrameResult` per frame with `frame_number` u32, `outcome`, `bytes` u32, `elapsed_us` u32 (from the first write to the client until its ack: `FrameAck.elapsed`) and `queued_us` u32 (time the frame waited in the gateway before its first write).

| `outcome` | From `hx_transport::AckOutcome` | Meaning |
|---|---|---|
| `DELIVERED` | `Delivered` | The client received the whole frame (stream completion on QUIC, `0x09` ack on WebSocket) |
| `CANCELLED` | `Cancelled` | The gateway reset the stream (`STALE_FRAME`), by its own decision or on `cancel_frames` |
| `REJECTED` | `Rejected(code)` | The client stopped the stream |
| `DROPPED` | (gateway only) | The gateway discarded the frame without starting to send it (window full, no client, resync discard) |

`ConnectionLost` is not sent; the client connection ending is followed by `stop`. Feedback arrives on `ctl`, so a congestion signal is never stuck behind video. The session's controller (1F) uses `elapsed_us`, `queued_us`, the `DELIVERED` rate and the `CANCELLED`/`DROPPED` counts to step its bitrate ladder (S2: settled near 3.5 Mbps at 150 ms RTT, 10 Mbps and 1% loss) and to decide when to send `cancel_frames` and force a `RESYNC` IDR. Feedback for one frame is sent at most once; a result for an unknown frame number is ignored by the session.

### 15.4 Audio (reserved)

`kind 0x11` is the protocol.md §7.2 datagram body (`seq`, `timestamp`, one Opus packet, 10 ms frames) as a media-lane frame. It is not produced in Phase 1: the `AUDIO` feature bit is 0 in `info`, and a `0x11` frame while the feature was not negotiated is a violation. Audio is loss tolerant: the gateway forwards it as a datagram and drops it rather than queueing it.

## 16. Bulk lane (`bulk`)

Clipboard and files use the transfer shape of protocol.md §9.4 (header, data chunks, end, abort) on one lane, so many transfers share one low-priority connection and cannot delay anything else.

- **IDs**: the gateway allocates odd ids and the session even ids; an id already in use is a violation. `TransferOpen.channel` is `CLIPBOARD` (protocol channel `0x07`) or `FILE` (`0x08`); its `header` is the protocol `TransferHeader` (`mime`, `name`, `size`) under the same validation (printable-ASCII `mime`, the file-name rules of protocol.md §3.1, empty `name` for the clipboard). The gateway applies those rules to every header the session sends **before** it opens a client stream.
- **Size**: the receiver counts bytes; fewer or more than `size`, or a clipboard over 64 MiB, aborts that transfer (`TRANSFER_ERROR`) and the lane continues. The file limit is `max_file_bytes` (default 4 GiB, configurable lower) in both directions; the protocol sets none yet (§21 follow-up).
- **Flow control**: a byte stream gives per-lane, not per-transfer, flow control. The gateway reads a transfer's data only while it holds less than 1 MiB unread for it and 4 MiB for the link, so a stalled client stream pauses the bulk lane and never `ctl` or `media`. One slow transfer can delay other transfers; accepted.
- **Policy**: the gateway enforces the device's clipboard and file settings in both directions (drops the data and aborts), and also tells the session through `StreamConfig` so that it does not read the selection at all. Clipboard transfers from the session are limited to 4 per second.
- **Names are hints.** The session writes received files into a directory of its own choosing (`~/Downloads/hx-received/`), picks its own file name, never overwrites (`O_EXCL`), never follows symlinks (`O_NOFOLLOW`), and creates the file with mode `0600`. The gateway never treats a name as a path, and forwards the session's names to the client only after the protocol.md name validation, as data shown in the transfer dialog and never as UI text (§19.1, rule 3).

## 17. Priorities and backpressure

The requirement: **input never waits behind video**, and video is dropped or cancelled, never queued without bound.

1. **Lanes separate sizes.** Video (up to `max_frame_bytes`, 4 MiB by default), cursor shapes and transfers each have their own connection or direction; `ctl` G → S carries only messages of at most 16 KiB.
2. **The gateway's writer for `ctl` G → S** is a single task with queues drained in strict order: **P0** `input` events (ordered, bounded at 4 096; gatewayd first rate limits what a client may send to 2 000 input events per second, and a client that exceeds that is closed with `PROTOCOL_ERROR`), then the single-slot **`mouse`** (latest wins: a newer motion replaces an unsent one, absolute and relative merged as in protocol.md §7.1, `MouseCoalescer`); **P1** `frame_feedback`, `request_idr`, `reconfigure`, `start`/`stop`, `ping`; **P2** `transport_stats`, `client_stats`, `goodbye`. A key or button always goes out before pending motion that arrived after it. **If the queues back up because the session does not read** (a write on `ctl` makes no progress for 2 s, or the P0 queue fills while the client is within its rate limit), that is a **link fault** (§19.2), not a client `PROTOCOL_ERROR`: the client is not at fault and is sent `Goodbye(INTERNAL_ERROR)` as for any link fault. Button events carry absolute coordinates, so a coalesced motion cannot misplace a click.
3. **The session's reader for `ctl` G → S** runs on its own thread, independent of the encode pipeline, and injects input with the XTest backend straight from it. The encoder threads cannot delay input.
4. **The gateway's reader for `ctl` S → G** parses cursor, `stream_format`, `cancel_frames` and `stats` in a task separate from the media reader and the bulk reader. Cursor positions coalesce to the newest within 1 ms; a shape is never overtaken by a later position (the protocol.md ordering rule).
5. **Video**: drained promptly, bounded window, cancel or drop with feedback, resync by IDR (§15.2). **Bulk**: lowest priority; the gateway yields after every 256 KiB so it cannot monopolise the runtime.

## 18. One active client per desktop and takeover

v1 has one active client per desktop. The session link knows clients only through `epoch` (§14.1); all policy sits in gatewayd.

- A second client that authenticates (pinned key and PIN passed) while another is active **takes over**, subject to a per-server policy `takeover` ∈ `allow` (default) or `deny` (the newcomer is answered `BUSY`). Takeovers are **rate limited**: at most 3 per 10 minutes per desktop, after which the newcomer is answered `BUSY` (so two devices cannot fight each other, or a stolen device keep kicking the owner off). The default is `allow` because a user switching devices must not be locked out by their own stale session; both clients have passed authentication, and the displaced one is told.
- Takeover sequence in gatewayd, in this order: (1) stop forwarding the old client's input and send `input{release_all}` to the session; (2) cancel the old client's in-flight frames (`CANCELLED`) and abort its transfers (`TransferAbort`); (3) tell the old client it was displaced: `Goodbye` with the `TAKEN_OVER` close code (a protocol.md follow-up, §21; until it exists `BUSY` with a fixed text) and the new device's sanitized name, so that the displaced client's UI can offer a **"revoke that device"** action (a stolen-then-used device is the likely reason to be displaced); the event is also written to privd's audit log (`RecordEvent` `TAKEOVER`); (4) increment `epoch` and send `start{epoch, config}` for the new client, then expect `stream_format` with the same `epoch` and an IDR `RESYNC` frame. Frame numbers keep counting, so the new client's reorder window starts clean.
- The session resets its congestion controller on `start`, discards feedback tagged for earlier frames and re-sends the cursor shape. Clipboard and transfers are per client and are not carried across.
- Only the current `epoch` may send input to the session: gatewayd forwards nothing from a client that is not the active one.
- When the last client leaves, gatewayd sends `stop`, keeps the link for 30 s (so a reconnect is instant), then closes `bulk`, `media` and `ctl`. The next authorized client redials.

## 19. Untrusted input and fault handling

### 19.1 Rules gatewayd follows for every session-supplied byte

1. Lengths are checked against §13 **before** any allocation; buffers come from fixed pools; no allocation is sized by a session-supplied value beyond those limits.
2. All integers are range-checked (frame numbers, sizes, `payload_len == length - 21`, coordinates, counters); statistics use saturating arithmetic.
3. **Session text is never shown in the client UI.** Strings are length limited and sanitized (control and ANSI characters removed) and go only to logs and the admin API; a client receives event *kinds and numeric codes*, never a session-supplied string (`info.software`, `event.message` and `goodbye.message` are log-only). The one exception is a file name in a transfer header, which has passed the protocol.md validation and is shown as data in the transfer dialog, never as a label or message. Session-supplied text is never used as a path, command or URL.
4. Cursor, transfer-header and file-name content gets the same validation as when a client sends it (protocol.md §3.1, §5.4, §5.5), before any of it is forwarded to a client.
5. Unknown protobuf fields and `oneof` variants are ignored and counted; undecodable bodies are violations.
6. Rates are enforced per message class (§13); the gateway never spends unbounded CPU or memory because the session is chatty.
7. The gateway never sends anything secret to the session, and never derives behaviour from where the session says it is, who it says it is, or what version string it claims, beyond the protocol version already negotiated.
8. No descriptors: every lane is read with `recvmsg`, and any control message or `MSG_CTRUNC` is a violation (the rule of §3).
9. The link parser (framer, message decoding, header, Annex B/SPS and transfer validation) lives in a module or crate that is `#![forbid(unsafe_code)]`, with fuzz targets for 1H: the lane framer, `SessionToGateway` decoding, media-header validation, the Annex B/SPS check, `TransferOpen` validation and cursor-shape validation. Running the relay in a separate, even more restricted process is considered later (§22, Deferred).

### 19.2 Faults and recovery

A **violation** (malformed frame or preamble, forbidden kind, oversize length, structural media-header error, a byte on an unused direction, more frames per second than the §13 frame-count limits allow) or a sustained rate or byte-budget overage (3 consecutive seconds) or a ctl write stall (§17) closes all three lanes, increments a per-link fault counter, logs a rate-limited warning with the sanitized reason, sends the client `Goodbye(INTERNAL_ERROR)` if one is connected, and leaves gatewayd otherwise unaffected. Redialling uses exponential backoff 1, 2, 4, … up to 30 s. After 5 faults within 10 minutes gatewayd asks privd for `RestartSession` (class A, so rate limited by privd); after 3 restarts in an hour it stops redialling quickly and reports the desktop as `session_unavailable` in status, so the app can say so (a bad session package or malware, the user's call). **There is a way back without an operator:** while `session_unavailable`, gatewayd retries once every 10 minutes (a single dial with the full validation of this section), and also immediately after privd reports the desktop restarted or the session package updated; the first clean handshake clears the state. A violation never crashes gatewayd: parse errors are values.

### 20.1 To the client protocol (protocol.md)

|---|---|

### 20.2 To the capture and encode pipeline (what 1F implements)

`apps/hx-session` currently exposes the protocol-independent media path in `hx_session::pipeline`. The link layer sits on top of it and uses only this API:

| Link | `hx_session` API |
|---|---|
| `start` | `Pipeline::start_x11(PipelineConfig { encoder.bitrate_kbps / fps, max_fps, .. })`, or resume a warm pipeline; the first frame follows `Control::request_idr()` |
| `stop` | `Pipeline::shutdown()` (or park it; CPU must reach about zero within 1 s) |
| `reconfigure.bitrate_cap_kbps` | The 1F congestion controller's ceiling; the rate it picks goes to `Control::set_bitrate_kbps` (100 to 100 000, no encoder reopen) |
| `reconfigure.max_fps` | `Control::set_max_fps` (1 to 240) |
| `reconfigure.width/height/scale` | `Control::request_resize(Size)`; a refusal appears in `StatsSnapshot::errors` and becomes `event RESIZE_REFUSED`; the resulting size is announced by `stream_format` |
| `request_idr` | `Control::request_idr()` |

## 21. Implementation notes and follow-ups

Not part of the contract; for the people implementing it. Each follow-up names its owner.

1. **`hx-ipc` crate (1C).** One new internal crate holds the framing (§4, §13), the `hx.privd.v1`, `hx.gatewayd_admin.v1` (protobuf identifiers cannot contain a hyphen) and `hx.link.v1` messages and helpers. It depends on `hx-proto` for the shared `hx.v1` types (`InputEvent`, `CursorEvent`, `TransferHeader`, `ClientStats`, `VideoCodec`), and splits the privd side and the link side by Cargo feature, so that `hx-session` does not compile the privd messages (and nothing pulls in `quinn`). **Status:** the crate exists (`crates/hx-ipc`; features `privd` and `link`, `hx-session` enables only `link`), architecture §3 and tech-stack.md are updated, and it adds only `zeroize` and `rustix` (`net`: `recvmsg`, `SO_PEERCRED`). `mlock`, `PR_SET_DUMPABLE` and `openat2` belong to privd itself, the HPKE implementation arrives with the Phase 2 sealed form (only the proto fields are reserved), and the H.264 Annex B / SPS check of §15.1 belongs with the gateway's media path.
2. **`hx-provision` follow-ups (1D):** (a) a device-add call on the Incus client for the proxy device (§6.11); (b) a standalone "check current password, set password" entry point on the post stage's stdin-file mechanism, shielded against cancellation (§4, §6.9); (c) an API that exposes the Incus background operation so privd can cancel it and wait (§4); (d) setting limits on a live instance including the root disk size (§6.8); (e) recipe vars for `settings` (hostname, timezone, locale, keyboard; §6.5); (f) privd uses the existing `Catalog::embedded()` / `embedded_source()` (recipes compiled in, §6.5), with a CI check that the embedded set equals `recipes/`; **and** `hx_provision::Secret` must not be `Clone` and must zeroize on drop, including copies made by `Secrets` (today `Secret` and `Secrets` derive `Clone`); (g) the Docker disable path and the host-network-only fallback (§6.9); (h) teardown helpers that delete only marked objects (§6.13); (i) `ExecSpec` has no user field, which matters only if `hx-session` ever becomes a user unit (§6.11). ## 22. Decisions and deferred items

### Decisions

Answers to the open questions of v0.1, taken after the security review.

1. **The device registry stays in gatewayd** (§2). PIN and Linux-password verifiers are `HMAC(pepper, Argon2id(secret))` with the HMAC computed by privd. It exposes **no MAC oracle**: `PepperVerify` returns only yes or no and counts failures globally per purpose (PIN 10/h and 50/day, PASSWORD 5/h and 20/day, then locked until an Admin `ResetLockout`), and `PepperEnrol` returns a MAC only to set a verifier (Gateway: 5/day after setup) (§5.3, §6.15). A stolen registry can therefore be guessed only online, through failure-capped verification. The `PASSWORD` cap can be used as a lockout lever by an internet attacker once web login exists (accepted; §5.3). Registry changes are recorded in privd's audit log (`RecordEvent`) and shown to all paired devices. The residual risk of a memory-resident gatewayd is stated in §1.2.
2. **Phase 1 accepts the plain Linux password passing through gatewayd** (one-liner path). Phase 2 secrets (Drive token, backup key) use the sealed, owner-authenticated, nonce-bound form of §5.2, whose fields are reserved now. Conditions: the current-password check (§6.9) runs a fixed-argv helper shipped in privd's verified `hx-session` package (a static crypt/yescrypt checker) and trusts only its exit status; the current password travels the same swept stdin-file path as `chpasswd`; and the failure caps of decision 1 apply.
3. **The setup window stays for the one-liner path** (2 hours by default, extendable by Admin only; §5.1). In the SSH install path the password and Drive token go over SSH to the root installer (an `Admin` caller), which writes the verifiers through the admin socket, so gatewayd never sees them.
4. **Takeover default is `allow`** (§18): the displaced client gets a `TAKEN_OVER` code and a "revoke that device" action; takeovers are rate limited (3 per 10 minutes) and audited. The `TAKEN_OVER` close code is a protocol.md follow-up (§21, item 4).
5. **A numeric-only `ServerStats` message is added to protocol.md** (follow-up, §21 item 4); session text is never forwarded to a client (§19.1, rule 3).
6. **Docker enable**: Gateway only while the setup window is open; Admin-only afterwards (`hx-agent docker enable`); `DisableDocker` stays open to Gateway (§5.1, §6.9, §7 rule 5).
7. **File size**: default maximum 4 GiB, configurable lower, enforced in both directions; a protocol.md follow-up (§21 item 4).
8. **Hostile video**: both layers. gatewayd checks Annex B structure and, on key frames, the SPS dimensions (§15.1); the client decodes in a sandbox with a `max_pixels` limit and is fuzzed (1G/1H).
9. **Schemas live in a new internal `hx-ipc` crate** that depends on `hx-proto` for the shared `hx.v1` types, with the privd and link modules split by feature (§21 item 1). Architecture §3 and tech-stack.md are updated when the crate is added in 1C.
10. **Proxy-device semantics** (`uid`, `gid`, `mode`, `security.uid`/`security.gid` under an isolated idmap; symlink and replacement test; restart and reboot; throughput) **are verified on real Incus as the first step of 1C implementation** (§11). There is no fallback to a root-identity connect: a failure reopens the design.
11. **Single desktop in v1.** Multi-desktop isolation, the device-to-desktop mapping and per-desktop link directories are deferred.
12. **Fetcher rules are contract-level now** (§6.12: dynamic user, no capabilities, no `AF_UNIX`, timeouts, size quotas, read-once verified copy, strict version regex, monotonic manifest timestamp, safe extraction); the sandbox details belong to 1C and 1D.
13. **Unit naming.** The streaming daemon is `hx-session.service` (a system unit running as the desktop user, started through `hx-session.socket`, §11); the recipe unit that runs `xfce4-session` is renamed (for example `hx-xsession.service`), a 1D/recipes follow-up (§21 item 3).
14. **The one-liner carries no token** (owner 1E and the wizard): the installer prompts for it on `/dev/tty` with hidden input and hands it to gatewayd as the `CreatePairingToken` secret frame (§9); `--token` in argv is only for unattended use and is documented as weaker (`sudo` logs argv to the auth log and journal, shells keep history; §5.2).

### Deferred

- **privd-backed signing oracle** for the identity key (a rustls custom `SigningKey` that asks privd for each handshake signature), the target design that takes key impersonation out of a gatewayd compromise (§2.1).
- **A separate, more restricted relay process** for the session link parser, if the in-process parser plus `forbid(unsafe_code)` and fuzzing proves insufficient (§19.1).
- **Owner-key-signed Docker enable** requested from the app after setup (§5.1).
- **Multi-desktop** isolation and per-desktop link directories (decision 11).
- `HOST_NETWORK_ONLY` Docker mode, `UpgradeIncus`, and the Phase 2 commands, which stay named and `UNIMPLEMENTED` (§6.9, §6.13, §6.14).
- Fetcher sandbox profiles and the signature scheme for prebuilt images (1C, 1D).
- The pairing-exchange hook that delivers privd's recipient key without SSH (1B).
- An augmented PAKE (SPAKE2+) for pairing, so that a stolen server-side verifier cannot be used to pair (longer-term option for 1B).
