# Internal IPC contracts

Status: draft v0.1 (2026-11-20), written for review **before any implementation** (execution-phase.md, "Contracts before consumers"). Nothing in this file exists in code yet.

Two contracts between hash-xcreen's own server-side processes:

1. **`hx-privd` command set** (Part 1, §3–§9): what the unprivileged `hx-gatewayd` (and the root CLI and installer) may ask the root `hx-privd` to do, over a unix socket.
2. **Session link** (Part 2, §10–§20): how `hx-gatewayd` talks to `hx-session` inside the desktop container, over a unix socket exposed into the container.

The client wire protocol is a third contract and lives in [protocol.md](protocol.md); this file only refers to it. Design background is in [architecture.md](architecture.md) §2, §4, §5, §8 and §9; the library that `hx-privd` drives is `crates/hx-provision` (its README, "Caller obligations for `hx-privd`", is binding for everything below).

Conventions: "MUST", "SHOULD" and "MAY" are used in the RFC 2119 sense. Integers outside protobuf are little-endian. Sizes are in bytes unless a unit is given. A "validation rule" is enforced by the receiver before it acts or allocates.

## 1. Trust model

### 1.1 Processes and principals

```
 client ⇄ (QUIC / WebSocket, TLS) ⇄ hx-gatewayd ──────────────┐
                                      │  privd.sock            │ Incus proxy device
 hx-agent CLI (root) ─── privd.sock ──┤  (§3)                  │ (Part 2, §11)
 installer    (root) ─── privd.sock ──┤                        ▼
                                      ▼                  hx-session (desktop user,
                                  hx-privd (root) ──► Incus      inside the container)
                                      │    unix socket
                                      └─► update fetcher, backup worker (sandboxed children)
```

| Principal | Identity on the privd socket | Trust |
|---|---|---|
| `Gateway` | uid of the `hx-gatewayd` system user | Low. Internet-facing; assume it can be compromised through a parser bug. |
| `Admin` | uid 0 (the `hx-agent` CLI, the installer, root's own tools) | Full. Root on the host is outside the threat model (architecture §8.1). |
| anyone else | any other uid | Refused at connect; no response is sent. |

`hx-session` is not a privd principal at all. It talks only to `hx-gatewayd`, over the session link, and is treated as **hostile input** there (malware in the desktop runs as the same user).

### 1.2 What a compromised gatewayd must not achieve

| Goal of the attacker | Why it fails |
|---|---|
| Run code as root | No command executes caller-supplied programs, paths, arguments, environment, recipes or Incus configuration. Every target (instance, pool, device, file, URL) is derived by privd from constants and its own state (§7). |
| Reach other containers or the host's services | Only one hash-xcreen desktop exists per server in v1, named by privd. The only device privd ever attaches is the link proxy device, whose host path privd computes (§7, rule 2). The host firewall, ACL and sysctl are generated by privd and cannot be influenced by the caller. |
| Read the Drive token, the backup key or the recovery key | They are stored root-only, loaded only by privd and the backup worker (§2). Where a client must hand one to the server, it travels sealed to a key only privd holds (§5.2). |
| Exhaust the host | Every command is bounded: argument limits, per-command rate limits, a global concurrency cap, per-desktop locks, deadlines, disk guards (§8). |
| Switch off isolation silently | The only commands that reduce isolation are `EnableDocker` (explicit acknowledgement, roll back on failure, fail closed) and, for `Admin` only, `allow_private_networks`. Both are logged. |
| Persist as root | Updates are accepted only if signed by an embedded minisign key and not older than the running version (§6.12). |

**Residual power of a compromised gatewayd** (accepted, because gatewayd is the relay by design): it sees and can drive the desktop's screen, keyboard, clipboard and files; it can read and rewrite the device registry; it can start, stop and restart the desktop, change its limits within the bounds of §6.8, change the desktop user's password, create a few manual snapshots, enable Docker after the acknowledgement flag, and trigger an update to an already-verified newer release. That ceiling is the contract of the `Gateway` command set; any new command must justify its place in it.

| Item | Location | Owner and mode | Who reads it |
|---|---|---|---|
| **Device registry**: paired devices (public keys, names, created/last-seen), revocation state, the PIN's Argon2id hash and failure counters, pairing-token state | `/var/lib/hx-gatewayd/registry` (the unit's `StateDirectory`) | `hx-gatewayd`, 0700 | `hx-gatewayd` only. The CLI reaches it through gatewayd's admin socket (§9), not by file. |
| Agent identity key and ACME account key | `/etc/hx/creds/*.cred`, encrypted with `systemd-creds` (TPM-backed where available) | root, 0600 | Delivered to gatewayd with `LoadCredentialEncrypted=` (tmpfs, visible to that unit only). gatewayd needs both: it terminates TLS and runs ACME. |
| **Drive refresh token, backup repository key, recovery-key material** (Phase 2) | `/etc/hx/creds/` as above | root, 0600 | `hx-privd` and the backup worker only. **Never** loaded into gatewayd. |

| privd policy (max desktops, host reserve, update channel, takeover limits) | `/etc/hx/privd.toml` | root, 0644 | `hx-privd` at start. Never writable or influenceable through the socket (the channel is changed by `Admin` through the CLI, which edits this file). |
| Desktop metadata (state, username, recipe id, Docker acknowledgement, created) | Incus instance config keys `user.hx.*` | Incus | privd. After creation privd reads the username and recipe from here and never trusts the caller to repeat them. |
| Linux password | Never stored by hash-xcreen. Set inside the desktop; only the shadow hash exists, in the container. | n/a | n/a |
| Link sockets | `/run/hx/link/` | root:`hx-gatewayd`, 0750 (§11) | gatewayd connects; it cannot create or replace entries. |
| privd socket | `/run/hx/privd.sock` | root:`hx-gatewayd`, 0660 | §3 |

Why gatewayd owns the registry: it is needed on the pre-authentication path of the internet-facing process and holds nothing that grants root (public keys and an Argon2id hash); putting it in privd would route pre-auth data through the root daemon and add a command surface for no isolation gain, because a compromised gatewayd already controls who gets in. Revocation also has to close live sessions, which only gatewayd can do. Consequences: the PIN is verified and its hash stored by gatewayd, so there is **no privd command for the PIN**; "store the PIN hash" (architecture §5.3, stage 8) is a gatewayd-local step.

# Part 1: the `hx-privd` command set

## 3. Transport and peer authentication

- **Socket**: `/run/hx/privd.sock`, a unix stream socket created by systemd socket activation (`hx-privd.socket`: `ListenStream=/run/hx/privd.sock`, `SocketUser=root`, `SocketGroup=hx-gatewayd`, `SocketMode=0660`, `Accept=no`). `/run/hx` is root:root 0755. privd inherits the fd, so it needs no filesystem permission to create it and the socket survives a privd restart (an update re-execs privd without dropping gatewayd's connection queue).
- **Peer authentication**: on every accept privd calls `getsockopt(SO_PEERCRED)`. The group bits on the socket are only a first filter. The allowlist is `{0, uid(hx-gatewayd)}`; the gateway uid is resolved by privd at start from the fixed user name compiled into the binary, never from a configuration value or from anything received over the socket. Any other uid is closed without a reply and logged. Where `SO_PEERPIDFD` exists the pid is recorded for the audit log; it is not used for decisions.
- **Self-checks at start** (privd refuses to start otherwise): the gateway user is in none of the `incus`, `incus-admin`, `docker` or `disk` groups; the Incus socket is not readable by the gateway uid; `/run/hx/privd.sock` has the mode and owner above.
- **No descriptor passing**: privd never receives file descriptors. It reads with plain `recv` and closes any connection whose ancillary data is non-empty (`MSG_CTRUNC` or any control message).
- **Roles**: the peer uid selects the role (`Gateway` or `Admin`) for the life of the connection. The role is never a field in a message. A command not allowed to the role is `PERMISSION_DENIED`.

## 4. Framing, messages and errors

**Framing.** A deliberate variation of `hx-proto`'s reliable-stream framing (`u32` little-endian length, then a protobuf message): the same length prefix and the same rule that a zero or oversized length, a truncated frame or a message that fails to decode closes the connection, plus one **kind** byte so that secrets can bypass the protobuf decoder (§5.1):

```
+----------------+---------+------------------------+
| length (u32 LE)| kind u8 | body (length - 1 bytes)|
+----------------+---------+------------------------+
```

`length` counts the kind byte and the body and is checked **before** anything is allocated.

| Kind | Body | Maximum `length` |
|---|---|---|
| `1` Message | one protobuf `Frame` (below) | 65 536 |
| `2` Secret | `request_id` (u64) + `slot` (u8) + raw secret bytes (§5.1) | 8 192 |

Protobuf (`prost`) is used because the rest of the project already uses it, it versions by field number, and the request/response messages are small. The messages are specified here by table; the schema file is to be generated into a shared crate (open question 9). Unknown fields are ignored; field numbers are never reused.

**`Frame`** (a `oneof`; exactly one variant, else invalid):

| Variant | Direction | Meaning |
|---|---|---|
| `Hello` {`major`, `minor`, `software` (≤ 64)} | caller → privd, first | Version handshake. privd requires the same `major` and answers `HelloAck`; a different major is `FAILED_PRECONDITION` and a close. Components ship from one release, so a mismatch means an update is half done and gatewayd restarts. |
| `HelloAck` {`major`, `minor`, `privd_version`, `phase` (§5.1), `role`} | privd → caller | `role` echoes the role privd derived, for diagnostics. |
| `Request` {`request_id` u64, `deadline_ms` u32, `secret_slots` (repeated `SecretSlot`), `command` (`oneof`, §6)} | caller → privd | `request_id` is chosen by the caller, non-zero, unique on the connection (a repeat is `INVALID_ARGUMENT`). `deadline_ms` may only shorten the command's maximum deadline (§8); 0 means the maximum. |
| `Cancel` {`request_id`} | caller → privd | Cancel the in-flight request; an unknown id is ignored. |
| `Progress` {`request_id`, `stage`, `index`, `total`, `step` (≤ 128, sanitized), `percent` (0–100 or 255 for unknown), `ok`} | privd → caller | Zero or more per request, before its `Response`. |
| `Response` {`request_id`, `result` (`oneof`: a per-command result or `Error`)} | privd → caller | Exactly one per request. |

**Connection rules.** `Hello` within 5 s of accept, else close. The body of a frame must arrive within 5 s of its header. A connection idle for 10 minutes is closed (callers reconnect). privd allows **one request in flight per connection**; a second `Request` before the `Response` is `RESOURCE_EXHAUSTED`. `Cancel` and `Ping` are the only frames accepted while a request runs. Parallelism comes from several connections (§8). Requests are processed in arrival order per connection.

**Cancellation.** `Cancel`, a closed connection, and an expired deadline all cancel the running command. Commands are cancellable at every await point (dropping the `hx-provision` future abandons the Incus operation); on cancel privd runs the command's cleanup (§6.4 for `CreateDesktop`) and answers `CANCELLED` or `DEADLINE_EXCEEDED`. A cancelled command never leaves a half-applied state it did not own; the "converge" semantics below make a retry safe.

**Progress streaming.** Long commands (`SetupHost`, `CreateDesktop`, `EnableDocker`, `ApplyUpdate`, Phase 2 backups) emit `Progress` frames. They map `hx_provision::Progress` (`Started`/`Finished` with `stage`, `index`, `total`, `step`, `elapsed`, `ok`) one to one and add coarse stages not in that type:

`stage` ∈ `PREFLIGHT`, `HOST`, `IMAGE_FETCH`, `IMAGE_IMPORT`, `BUILD`, `LAUNCH`, `POST`, `DOCKER`, `SESSION`, `UPDATE`, `BACKUP`, `RESTORE`, `DONE`.

Progress is lossy and bounded: at most 10 per second per request, at most 256 buffered per connection; when the peer reads slowly privd keeps the newest and drops the rest. A step description is `hx-provision`'s own text (recipe-defined, never container output), still passed through `sanitize`. The `Response` is never dropped; if the peer will not read it within 10 s privd closes the connection (the command's effect stands).

**Error model.** `Error` {`code`, `detail` (command-specific enum, optional), `message` (≤ 256 bytes, sanitized, never contains secrets or unsanitized container output), `retryable` (bool), `retry_after_ms`}.

| `code` | Meaning |
|---|---|
| `INVALID_ARGUMENT` | A validation rule failed. `message` names the field. |
| `PERMISSION_DENIED` | The role may not call this command, or the command may not take this argument from this role. |
| `FAILED_PRECONDITION` | Wrong state: setup window closed, desktop not ready, `needs_attention` set. `detail` says which. |
| `NOT_FOUND` | Unknown desktop or snapshot id. |
| `RESOURCE_EXHAUSTED` | Rate limit, concurrency cap, host headroom, pool space, desktop cap. Retryable with `retry_after_ms` where known. |
| `DEADLINE_EXCEEDED` / `CANCELLED` | Deadline hit or `Cancel` received. |
| `UNAVAILABLE` | Incus (or another dependency) cannot be reached. Retryable. |
| `UNIMPLEMENTED` | Command reserved or not available in this release. |
| `INTERNAL` | A bug or unexpected dependency failure; the detail is in the journal, not in the message. |

A *domain outcome* that the caller must act on is a successful `Response`, not an `Error` (for example Docker's `SelfTestFailed`, §6.9). Container-originated text is sanitized by `hx-provision` (control and ANSI characters removed, truncated) and is still untrusted: callers escape it for any UI.

## 5. Authorization and secrets

### 5.1 Command classes

privd authorizes by role and by **phase** (kept in `/var/lib/hx/privd-state`, root-only, one of `UNINITIALIZED`, `SETUP_OPEN`, `READY`; plus independent `needs_attention` flags per desktop, §6.9).

| Class | Gateway | Admin |
|---|---|---|
| `R` read-only | always | always |
| `A` routine (desktop operations) | when `READY`, or during `SETUP_OPEN` | always |
| `S` setup | only while `SETUP_OPEN`, with the restricted argument set | always, full argument set |
| `X` privileged | never | always |

`SETUP_OPEN` is opened only by `Admin` (`BeginSetup`, called by the installer after it has verified and installed the agent; it expires after at most 24 hours) and closed by `FinishSetup` (callable by Gateway or Admin once a desktop is `ready`) or by expiry. The window exists so that the app can drive the install over the paired channel (architecture §5.3 stages 4 to 8) without the gateway keeping standing power to create desktops or rebuild the host afterwards. It limits the damage from a gatewayd compromised *after* setup; it does not protect a compromise *during* setup, which is why the setup commands take only bounded, validated arguments anyway.

### 5.2 Secrets: how they travel and are held

Rules for every secret (Linux password, Phase 2 Drive token and backup key): never in argv, environment, a file path, a log line, an error message, a `Progress` step or a protobuf message; never written to disk by privd.

1. **Secret frames.** A request that carries secrets lists them in `secret_slots` (`slot` u8, `kind`, `sealed` bool, `length` u32) and sends one **kind `2` frame** per slot straight after the `Request` and before processing begins. privd reads these frames into `Zeroizing` buffers that are `mlock`ed and excluded from core dumps (`PR_SET_DUMPABLE=0` for the whole process, `RLIMIT_CORE=0`), without passing them through `prost`, so no intermediate heap copy exists. Missing, extra, oversized or late (5 s) secret frames reject the request. The `Request` struct has no field that can hold secret bytes, and secret types have a redacting `Debug`.
2. **Where each secret goes.**

| `kind` | Accepted forms | Length | Use |
|---|---|---|---|
| `USER_PASSWORD` | plain, or sealed | 1–1 024 bytes, no `\n`, `\r` or NUL (the `hx_provision::Secrets::with_user_password` rules) | stdin of `chpasswd` via `hx_provision`'s 0600 file in the 0700 work directory (no argv, no environment), then swept |
| `DRIVE_TOKEN` (Phase 2) | **sealed only** | ≤ 8 192 | Sealed into privd's credential store; handed to the backup worker as a repository handle, never as the raw token (architecture §9.4) |
| `BACKUP_KEY` (Phase 2) | **sealed only** | ≤ 8 192 | As above |

3. **Sealed secrets.** To keep the Drive token and backup key out of gatewayd even though the paired channel terminates there, the client encrypts them to privd's sealing key and gatewayd only relays ciphertext. Format: HPKE (RFC 9180) base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305; `info` = `hx-privd-secret/v1`; `aad` = `kind || desktop_id`; plaintext = `not_after_unix_s` (u64) ‖ value; privd rejects a box whose `not_after` has passed. Replaying a captured box only re-sets the same value, so no nonce store is needed. privd publishes the public key through `GetRecipientKey` (§6.13); the client must obtain it through an authenticated path, which **needs a hook in the pairing exchange owned by 1B** (open question 2). In Phase 1 only the password exists, it may travel plain, and gatewayd therefore sees it in memory in transit; it holds it in zeroizing memory for the shortest time and never persists or logs it.
4. **Gateway-side obligation.** `hx-gatewayd` holds a password only between receiving it from the client and the privd response, in `Zeroizing` memory, with no copy into logs, metrics or panics (a panic hook redacts). If gatewayd restarts mid-install the app resends it (the app still has it); nothing is stored for resuming.
5. **Process hygiene.** privd and the workers it spawns are started with a cleared environment and fixed argv from constants (never through a shell); nothing derived from a secret appears in `/proc/<pid>/cmdline`, `environ`, a unit file or the journal. This is what Gate 1's "no secret in any command line, log or process list" checks.

## 6. Commands

Common to every command: arguments are parsed into typed values at the boundary (parse, do not re-validate later; the typed value is what is used) and an argument not listed is ignored. **Converge** means the command drives the system to the described state and succeeds if it is already there. All mutating commands are written to the audit log (§8) with role, command, desktop id and outcome, never with argument values that could be secret.

Shared types:

- `DesktopId`: `^[a-z][a-z0-9]{0,11}$`. v1 allows exactly one desktop and the installer uses `main`. privd maps it to the instance name `hx-<id>`; the caller never supplies an instance name (hx-provision README, "Names and paths stay inside privd").
- `Limits` {`cpu` u32, `memory_mib` u64, `disk_gib` u64}; bounds in §6.8. `limits.processes` is not settable (always `DEFAULT_PROCESSES` = 8192, never unlimited).
- `Distro` ∈ `ubuntu-24.04`, `ubuntu-26.04`, `debian-12`, `debian-13`; `Desktop` ∈ `xfce`; `Preset` ∈ `basic`, `developer` (the `hx_provision::{Distro, Desktop, Preset}` enums; unknown values are `INVALID_ARGUMENT`).
- `Username`: `hx_provision::Username::new` (1–32 characters of `^[a-z_][a-z0-9_-]{0,31}$`, reserved names refused).

### 6.1 `Ping` (class R, both)

Returns `{privd_version, uptime_s}`. No side effects. Used for liveness.

### 6.2 `GetHostInfo` (R, both)

Returns the facts the app and the installer's preflight show: `privd_version`, `phase`, OS id and version, arch, CPU count, total and available memory (MiB), pool {exists, driver, total and free GiB}, Incus version (`Client::server_info`), `docker_on_host`, `host_firewall_loaded` (table `inet hx` present), `sysctl_ok`, `needs_attention` list, and whether a desktop exists. Read-only; deadline 10 s. Failure: `UNAVAILABLE` if Incus is down (the other fields are still returned in the success body with `incus` marked absent).

### 6.3 `BeginSetup` / `FinishSetup` (class X / A)

`BeginSetup` {`expires_in_s` 60–86 400, default 86 400}: Admin only, `UNINITIALIZED` or `READY` to `SETUP_OPEN`. `FinishSetup` {}: Gateway or Admin, `SETUP_OPEN` to `READY`; requires that at least one desktop in state `ready` exists unless called by Admin with `force`. Both converge.

### 6.4 `SetupHost` (class S)

Purpose: everything architecture §4.2 and §5.3 stages 4 to 6 require on the host: `ensure_host` (pool, bridge, ACL, profiles), the sysctl file, the nftables host ruleset and the Docker `DOCKER-USER` rules.

| Argument | Type and validation | Who |
|---|---|---|
| `pool_size_gib` | u32, 12–200 (`MIN_POOL_GIB`/`MAX_POOL_GIB`); default `default_loop_size_gib(free)`; also at most 60% of the free space of the Incus storage directory's filesystem at call time. Maps to `PoolSource::LoopFile`. | Gateway, Admin |
| `pool_device` | A block-device path under `/dev/`. privd itself verifies, as root, what the README demands of the installer: it is a block device (not a symlink target of a non-device), a whole disk, not mounted, no mounted or in-use partitions, no filesystem or RAID/LVM signature (`blkid -p`), not the device holding `/`. Maps to `PoolSource::Device`. | **Admin only** |
| `allow_private_networks` | bool, default false. Maps to `HostSpec::allow_private_networks`; reducing isolation, so installer option only. | **Admin only** |
| `extra_host_addresses` | up to 16 IPs. | **Admin only** |
| `ipv4` | `auto` or `a.b.c.d/nn` (`/16`–`/29`, a private range). Default `auto`. | **Admin only** |

privd does:

1. `HostSpec`: `Naming::production()` (never a caller prefix), `host_addresses` = **every** address of every interface except our own bridge, enumerated by privd over netlink (public, private, Docker bridge gateways), plus `extra_host_addresses`; `HostSpec::validate()`.
2. `hx_provision::ensure_host`. Idempotent; nothing is deleted.
3. Take `HostReport::host_firewall` (privd calls `nft_host_protection` itself; the text is never accepted from a caller), check it with `nft -c -f -`, load it with `nft -f -` (the ruleset on stdin), and persist it to `/etc/hx/host-firewall.nft` with a oneshot unit `hx-host-firewall.service` that loads it at boot, ordered before `incus.service`. Done when `nft list table inet hx` shows the table.
4. Write `/etc/sysctl.d/90-hx-incus.conf` from a constant template (`fs.inotify.max_queued_events`, `max_user_instances`, `max_user_watches` = 1048576; `vm.max_map_count` = 262144) and apply it with `sysctl -p <file>`; verify by reading the values back.
5. If a host Docker is present (the `DOCKER-USER` chain exists): ensure the two accept rules for our bridge (`iptables -C` then `-I`, idempotent) and install `hx-docker-user.service`, ordered after `docker.service`, which re-applies them. If the rules cannot be applied, the response says so (`docker_user_rules: FAILED`) and `needs_attention` gets `HOST_DOCKER_FORWARDING`; the command still succeeds, because the desktop works without internet and the installer decides.

privd also re-runs steps 1 to 3 on its own at start and, after a 30 s debounce, whenever a host address appears or disappears (the README requires `ensure_host` to be re-run when `host_addresses` change). That is internal behaviour, not a command.

Output: `{pool, network, acl, desktop_profile, compat_profile` (each `Ensured`: created/existed/updated)`, gateway_ip, firewall_loaded, sysctl_applied, docker_user_rules}`. Idempotent (converge). Deadline 5 minutes. Progress stage `HOST`. Failure: each step is independently idempotent, so a failed `SetupHost` is simply called again; the error names the step (`detail` ∈ `POOL`, `NETWORK`, `NFT`, `SYSCTL`, `DOCKER_USER`). Incus down is `UNAVAILABLE`.

### 6.5 `CreateDesktop` (class S)

Purpose: create the desktop container, from a prebuilt image or by building on the server (architecture §4.3), through to `ready`.

| Argument | Type and validation |
|---|---|
| `desktop_id` | `DesktopId`. Refused if a desktop already exists (v1 cap, from `privd.toml`, default 1) unless this is a retry of the same id still in state `creating`/`failed`. |
| `distro`, `desktop`, `preset` | enums as above. |
| `username` | `Username`. |
| `image_mode` | `AUTO` (default), `PREBUILT`, `BUILD`. |
| `limits` | `Limits`, bounds in §6.8; omitted fields get privd defaults (all host CPUs; memory = host RAM minus the reserve; disk = 80% of the pool). |
| `docker` | bool, default false. If true, `docker_isolation_acknowledged` MUST also be true and the Docker flow of §6.9 runs after the post stage. |
| `settings` | `hostname` (RFC 1123 label), `timezone` (a name present in `/usr/share/zoneinfo`), `locale` (`^[a-z]{2,3}_[A-Z]{2}(\.UTF-8)?$` from an allowlist), `keyboard` (`^[a-z]{2}(\+[a-z0-9_-]{1,16})?$`). **Reserved**: the recipe vars for these do not exist yet in `hx-provision`, so a non-empty `settings` is `UNIMPLEMENTED` until 1D adds them (§21). |
| `image_file` | **Admin only**: path of an offline image under `/var/lib/hx/import/`, opened `O_NOFOLLOW`, a root-owned regular file, signature and checksum verified. Gateway: `PERMISSION_DENIED`. |
| secret slot 0 | `USER_PASSWORD`, required (plain or sealed, §5.2). |

privd does:

1. Authorize (class S), take the `desktop:<id>` lock, check the phase and the desktop cap, check free pool space against a minimum (≥ 8 GiB free and ≥ 15% free).
2. Load recipes from privd's installed, read-only recipe directory (`/usr/lib/hx/recipes`, shipped with and verified as part of the agent); **never** `Catalog::from_dir` of a caller-influenced path. `Catalog::resolve_for(RecipeId, addons, Some(&username))`.
3. Choose the image path (`AUTO`: reachability of the release host, free disk, download speed against the apt mirror; reason recorded). Download and signature/checksum verification of a prebuilt image is done by the sandboxed fetcher (§6.12) plus privd's own minisign and SHA-256 verification; privd imports it through the Incus REST API. The base image for the build path is a constant remote alias (`ImageSource::Remote` with a constant server, never a caller value).
4. `DesktopSpec::for_plan(name = "hx-<id>", Naming::production(), &plan, limits)`, `compat_profile` from `needs_compat_profile(&plan)`, then `orchestrate::finish_prebuilt` (prebuilt) or `orchestrate::build_on_server`. The post stage runs through `run_post_stage` (which sweeps `/run/hx-provision` before and after) with `Secrets::with_user_password`. The call must never be `apply_stage(.., Stage::Post, secrets, ..)` directly (README).
5. Write instance metadata: `user.hx.state=creating` first, then `user.hx.username`, `user.hx.recipe`, `user.hx.created`; `user.hx.state=ready` **last**, after steps 6 and 7 succeed.
6. Provision the session link (§6.10) and install `hx-session` (§6.10), so the version matches the agent.
7. Optional Docker (§6.9).

Idempotency and failure: a retry with the same `desktop_id` and arguments while the desktop is `creating` or `failed` destroys that unfinished instance (`destroy_instance`; it holds no user data yet) and starts again; a `ready` desktop with the same arguments returns success with its current report; with different arguments, `FAILED_PRECONDITION`. On any failure or cancel privd destroys the instance it created in this request, so no half-built desktop is left behind, and the error carries the failing stage. Output: `{desktop_id, path_taken: PREBUILT|BUILD, reason, timings, warnings (≤ 16, each ≤ 256 bytes, sanitized), docker (the §6.9 outcome, if requested)}`. Deadline 45 minutes (targets: prebuilt < 5 min, build < 20 min). Rate: 3 per hour. Progress stages `PREFLIGHT`, `IMAGE_FETCH`, `IMAGE_IMPORT`, `BUILD`, `LAUNCH`, `POST`, `SESSION`, `DOCKER`.

### 6.6 `GetDesktop` / `ListDesktops` (R, both)

`GetDesktop` {`desktop_id`} returns `{desktop_id, state (creating|ready|failed|stopped|running|starting), username, distro, preset, ip (bridge address), limits, docker (off|on|degraded), needs_attention[], session {installed_version, link_provisioned}, snapshots (count), created}` from `Client::get_instance`/`instance_state` and the `user.hx.*` keys. `ListDesktops` returns at most 8 of these. Deadline 10 s. `NOT_FOUND` for an unknown id.

### 6.7 `StartDesktop` / `StopDesktop` / `RestartDesktop` (class A)

{`desktop_id`, and for stop and restart `force` bool (default false)}. Calls `Client::set_state` (`Start`, `Stop`, `Restart`) with a 30 s graceful timeout; `force` skips the grace period. Converge: starting a running desktop succeeds. After a start privd waits for `wait_system_running` (60 s, `allow_degraded=false`) and reports `{running, degraded}`. Refused with `FAILED_PRECONDITION(ISOLATION_NOT_RESTORED)` for Gateway while that flag is set (§6.9); Admin's `StartDesktop` retries the rollback first. Deadline 2 minutes. Rate: 6 per minute per desktop.

### 6.8 `SetLimits` (A)

{`desktop_id`, `limits`}. Bounds, computed by privd from the host at call time:

- `cpu`: 1 ≤ cpu ≤ host CPU count.
- `memory_mib`: ≥ 1 024 and ≤ host RAM − max(1 536 MiB, 25% of host RAM) (headroom for the host and Incus).
- `disk_gib`: ≥ the desktop's current usage plus 2 GiB (never shrinks below use), ≤ pool free space. Not zero in any field (`Limits` rejects zero).

Applies `limits.cpu` and `limits.memory` with `Client::patch_instance_config` and the root disk size through the instance's root device (live where Incus allows; the response says `restart_required`). Never touches `limits.processes` or any other key. Converge. Deadline 30 s. Rate: 6 per hour.

### 6.9 `SetUserPassword`, `EnableDocker`, `DisableDocker`

**`SetUserPassword`** (A) {`desktop_id`; secret slot 0 `USER_PASSWORD`}. privd reads the username from `user.hx.username` (a caller-supplied name is not accepted), then changes the password through the same bounded path as the post stage (a `chpasswd` exec whose stdin file lives in the swept work directory). Converge (setting the same password is a no-op in effect). Rate: 10 per hour. Failure: `FAILED_PRECONDITION` if the desktop is not running. *Gap in hx-provision: it has no standalone "set password" entry point, only the post stage; §21.*

**`EnableDocker`** (A) {`desktop_id`, `acknowledged_isolation_warning` bool (MUST be true, else `INVALID_ARGUMENT`), `mode` ∈ `STANDARD` (default), `HOST_NETWORK_ONLY` (reserved: `UNIMPLEMENTED` until hx-provision supports it)}. privd records the acknowledgement time in `user.hx.docker_ack`, resolves the add-on with `Catalog::resolve_addon_for(id, Addon::Docker, Some(&username))` and calls `docker::enable_docker(.., DockerOptions::default(), ..)`. `allow_old_incus` is never set from a request (the field does not exist). The `DockerOutcome` is returned as a normal response:

- `Enabled {docker_version}`.
- `UnsupportedIncus {found, required, fallbacks}`: nothing was changed.
- `SelfTestFailed {isolation_restored, hint, output_tail (sanitized, ≤ 2 KiB), fallbacks}`.

**Fail closed.** If `isolation_restored` is false privd retries the rollback itself up to 3 times (the three allowed keys back to off, then restart). If it still fails, privd stops the desktop, sets `needs_attention=ISOLATION_NOT_RESTORED`, and refuses `StartDesktop` from Gateway until the rollback succeeds (Admin's `StartDesktop` retries it). This is the explicit handling of `DockerOutcome::SelfTestFailed::isolation_restored` that the README requires. Fallback 1 (Zabbly Incus) is class X (`UpgradeIncus`, §6.13); fallback 2 is reserved. Converge: an already-enabled desktop that passes the self-test returns `Enabled`. Deadline 15 minutes. Rate: 3 per hour. Progress stage `DOCKER`.

**`DisableDocker`** (A) {`desktop_id`}. Sets `security.nesting` and the two syscall intercepts back off (the three keys the recipe allowlist permits, nothing else) and restarts the desktop; Docker data in the desktop is untouched. Always allowed to Gateway because it only reduces exposure. Returns `{restarted}`. Rate: 6 per hour. The client must warn that open apps close.

### 6.10 `CreateSnapshot` / `ListSnapshots` / `DeleteSnapshot` (A)

Names are generated by privd: `hx-<kind>-<utc timestamp>-<4 hex>` with `kind` ∈ `manual` (Gateway or Admin), `preupdate` (privd, before an update), `backup` (Phase 2, privd only, tagged and removed by crash recovery).

- `CreateSnapshot` {`desktop_id`}: creates a `manual` snapshot with `Client::create_snapshot` (S3 measured 0.2–0.5 s). At most 3 `manual` snapshots; a fourth is `RESOURCE_EXHAUSTED`. Refused when pool free space is below 15% or 2 GiB. Rate: 6 per hour. Deadline 60 s.
- `ListSnapshots` {`desktop_id`} (R): the `hx-`-prefixed snapshots only, at most 64: `{name, kind, created, size}`.
- `DeleteSnapshot` {`desktop_id`, `name`} (A): `name` must match `^hx-(manual|preupdate|backup)-[0-9TZ-]+-[0-9a-f]{4}$` and exist. Gateway may delete `manual` only; Admin any `hx-` snapshot. A name outside the pattern is `INVALID_ARGUMENT`; privd never touches a snapshot it did not name. Idempotent (already gone succeeds).

### 6.11 `ProvisionSessionLink`, `InstallSession`, `RestartSession` (A)

**`ProvisionSessionLink`** {`desktop_id`}: ensures that the one Incus **proxy device** that exposes `hx-session` to gatewayd exists, with these properties (computed by privd, never given by a caller; the rationale and the alternatives are in §11):

| Property | Value |
|---|---|
| device name / `type` | `hx-link` / `proxy` |
| `bind` | `host` |
| `listen` | `unix:/run/hx/link/<desktop_id>.sock` |
| `connect` | `unix:/run/user/<uid>/hx-session.sock`, where `<uid>` is the desktop user's numeric uid from the recipe (1000), not read from the container |
| `uid`, `gid`, `mode` (the host-side listening socket) | the gatewayd uid and gid, `0600` |
| `security.uid`, `security.gid` (the identity the container side connects as) | the desktop user's uid and gid |

It also ensures `/run/hx/link/` exists as root:`hx-gatewayd` 0750 (so gatewayd can traverse it but cannot create, rename or delete entries, and cannot substitute a socket). Converge; the device persists across restarts and is the only device privd ever adds to a desktop. Returns `{socket_path}`. Rate: 6 per hour. *Gap in hx-provision: the Incus client has no device-add call; §21.* Failure: if the container does not accept the device `FAILED_PRECONDITION` with the Incus message sanitized.

**`InstallSession`** {`desktop_id`}: pushes the `hx-session` package for the desktop's distro from privd's own artifact store (`/usr/lib/hx/session/<distro>/`, minisign-verified with the agent release; the caller supplies no path, URL or bytes) into `/var/lib/hx/session/` in the container with `push_file`, installs it with a fixed `dpkg -i` exec (bounded output via `exec_captured`), and restarts the `hx-session` user unit. Converge (same version: no-op). Returns `{installed_version, restarted}`. Used at creation and after an agent update (architecture §5.5: "pushed into the container by the agent; only the streaming process restarts"). Rate: 6 per hour; deadline 5 minutes.

**`RestartSession`** {`desktop_id`}: restarts only the `hx-session` user unit (`systemctl --user`, as the desktop user via a fixed exec); user applications keep running (architecture §6, S2 lesson: `hx-session` owns the processes it manages). Gatewayd calls it after repeated link faults (§19.2). Rate: 6 per hour per desktop.

*Naming conflict to resolve with 1D:* `recipes/fragments/xfce-desktop.toml` currently names the unit that runs `xfce4-session` `hx-session.service`. The streaming daemon needs its own unit name (§21).

### 6.12 `CheckUpdate`, `ApplyUpdate`, `RollbackUpdate` (self-update hooks)

Network access is done by a sandboxed **update fetcher** that privd spawns on demand (a dedicated dynamic user, no capabilities, network only, writing into `/var/lib/hx/updates/`); root privd never speaks HTTP. privd verifies what the fetcher left.

- **`CheckUpdate`** (R/A, both) {}: the channel (`stable` or `beta`) comes from `privd.toml`, not the request. Spawns the fetcher, then verifies the signed release manifest. Returns `{current, available (optional), channel, verified: true}`. Deadline 60 s; rate 6 per hour.
- **`ApplyUpdate`** (A, both) {`version`}: `version` MUST equal a release privd has already fetched and verified: minisign signature valid against the **embedded current or next key** (installer rule, architecture §13), SHA-256 matches, `version` strictly newer than the running one (**no downgrade by request**), built for this arch. privd takes a `preupdate` snapshot of the desktop (best effort), unpacks to `/usr/lib/hx/<version>/`, flips `/usr/lib/hx/current` atomically, restarts gatewayd and then re-execs itself, answering the request first with `restarting`. A health check follows (privd status answers; gatewayd completes a Hello handshake on loopback; if the desktop runs, the session link handshakes): any failure within 90 s flips the symlink back, restarts, and records `needs_attention=UPDATE_ROLLED_BACK` with the reason. After a successful agent update gatewayd calls `InstallSession`. Rate: 2 per day; deadline 10 minutes; progress stage `UPDATE`.
- **`RollbackUpdate`** (X, Admin) {}: flips back to the previous retained version (two are kept). The signature rules still apply because the old files were verified when installed.

### 6.13 Admin-only commands (class X)

- **`DestroyDesktop`** {`desktop_id`, `confirm_destroy` true}: stops and deletes the instance (`destroy_instance`) and its `hx-` snapshots, removes the proxy device. Used by repair and by Phase 2 restore, and by `Uninstall`. Idempotent.
- **`Uninstall`** {`keep_desktop` bool, `confirm_destroy` bool (required true when `keep_desktop` is false)}. Idempotent and resumable (state kept in `/var/lib/hx/uninstall-state` until done; "every stage is idempotent", architecture §5.3). `keep_desktop=true`: removes the agent (units, sockets, binaries, `/etc/hx/creds`, registry, the link proxy device) but **leaves the desktop, pool, bridge, ACL, profiles, the host firewall unit and the sysctl file**, because removing the firewall would silently weaken a desktop that keeps running; the CLI says how to remove them later. `keep_desktop=false`: additionally destroys the desktop and its snapshots, then deletes the profiles, ACL, bridge and pool, the nftables table and unit, the `DOCKER-USER` rules and unit, and the sysctl file. It deletes only objects named by `Naming::production()` **and** carrying the hash-xcreen marker, never an object that merely has a matching name pattern, and never uninstalls Incus itself.
- **`UpgradeIncus`**: installs a newer Incus from the Zabbly repository (Docker fallback 1). Admin only because it changes host packages; **reserved in Phase 1** (`UNIMPLEMENTED`), the CLI documents the manual step.
- **`GetRecipientKey`** (R, both): returns `{key_id, public_key (32 bytes X25519)}` for sealed secrets (§5.2). No secret is involved.

### 6.14 Reserved for Phase 2 (named, not specified)

`BackupRun`, `BackupCancel`, `BackupStatus`, `ListBackups`, `SetBackupSchedule`, `SetBackupCredentials`, `VerifyBackup`, `PruneBackups`, `RestoreStart`, `RestoreStatus`, `RestoreConfirm`, `GenerateRecoveryKey`. In Phase 1 every one answers `UNIMPLEMENTED`. Constraints they must meet (so this contract does not need a breaking change):

- Gateway may request, observe and cancel; it never supplies a path, snapshot name, repository location or credential in the clear. `SetBackupCredentials` takes `DRIVE_TOKEN`/`BACKUP_KEY` **sealed only** (§5.2).
- privd takes the snapshot, attaches it read-only to the worker with the idmapped mount (architecture §9.4 step 2) and spawns the sandboxed worker; the worker never holds the Google credential, only a repository handle from privd.
- The recovery key is generated by privd/the worker and delivered to the client **sealed to the device key**, not as plaintext through gatewayd, since "shown once" must not mean "seen by gatewayd".
- `RestoreStart` restores through Incus (isolated idmaps, architecture §9.8 item 7), into a temporary instance, never replacing the live desktop before the boot check passes.
- A `backup` snapshot is always tagged so crash recovery can delete leftovers (architecture §9.6).

## 7. What privd refuses (confused-deputy rules)

privd is the deputy; gatewayd is the less-privileged caller. These hold regardless of what a request says:

1. **No caller-chosen names.** Instance, snapshot (other than the generated kinds), pool, network, ACL, profile and device names, `Naming`, `HostSpec`, `PoolSource` (except `LoopFile` size), `Catalog` roots and `DockerOptions::allow_old_incus` are never taken from a Gateway request. They are constants or derived by privd.
2. **No caller-chosen paths or addresses.** No host path, image URL or server, release URL, socket path, mount source or proxy `connect`/`listen` value. In particular the proxy device's host path is computed, because a proxy device whose `connect` pointed at `/run/hx/privd.sock` or `/var/lib/incus/unix.socket` would hand the container the keys to the host.
3. **No arbitrary execution.** No command takes a command line, shell string, environment, recipe text, `incus_config` key or file content. Every `exec` (host: `nft`, `sysctl`, `iptables`, `dpkg`, `systemctl`; container: `chpasswd`, `dpkg`, `systemctl --user`) is a fixed argv from constants, run without a shell, with a cleared environment, a timeout and a 64 KiB output cap.
4. **No Incus passthrough.** privd exposes no generic Incus REST call, device, profile or config edit. The only instance config keys it ever writes are the fixed set in `DesktopSpec::to_create`, the three Docker keys, `limits.cpu`/`limits.memory`, and `user.hx.*`.
5. **Privileged options stay with `Admin`.** `pool_device`, `allow_private_networks`, `extra_host_addresses`, `ipv4`, `image_file`, `UpgradeIncus`, `Uninstall`, `DestroyDesktop`, `RollbackUpdate`, `BeginSetup`, and a `FinishSetup` with `force`.
6. **Setup commands only in the window.** `SetupHost` and `CreateDesktop` from Gateway outside `SETUP_OPEN` are `FAILED_PRECONDITION`.
7. **Caps.** Not more than the configured number of desktops (1), limits above host bounds, unlimited `limits.processes`, more than 3 manual snapshots, a disk below current use.
8. **Only objects we own.** Destructive commands act only on objects whose names match our naming and which carry our marker (`user.hx.*` for instances, the hash-xcreen description for pool, network, ACL and profiles). Snapshots not matching the `hx-` pattern are never listed, created over or deleted.
9. **Secrets only as declared.** A secret of the wrong `kind`, a plain `DRIVE_TOKEN` or `BACKUP_KEY`, a secret outside a declared slot, or a secret in a protobuf field, is `INVALID_ARGUMENT`.
10. **Updates only forward and signed.** An unsigned artifact, a signature from a non-embedded key, a version not newer than the running one, or a version privd did not itself fetch and verify, is refused.
11. **Isolation first.** While `needs_attention` holds `ISOLATION_NOT_RESTORED`, Gateway cannot start the desktop.
12. **Container-originated data is never interpreted.** Output from the desktop is sanitized and truncated, is never used as a path, command, URL or Incus parameter, and is never read through host paths into the container filesystem (architecture §8.5): files in the container are accessed only through the Incus API, and `record-output` is never used.
13. **No descriptors, no ambient trust.** No file descriptors over the socket (§3); no authorization from the pid, the executable path or any message field.
14. **No new concurrency channels.** A command that is rate limited or locked out does not queue indefinitely (§8).

# Part 2: the session link

## 10. Purpose, topology and trust

`hx-gatewayd` relays media and input between a client (protocol.md) and `hx-session`, the process inside the desktop container that captures, encodes and injects. The session link is the unix-socket connection between the two. It carries:

- encoded video frames with what the gateway needs to build the media header (§15), and the cursor (§14);
- input events from the client, including a coalesced mouse-motion stream (§14);
- clipboard and file transfers in both directions (§16);
- per-frame delivery feedback and cancel signals from the gateway to the session's congestion controller, and cancel requests the other way (§14, §15);
- control: start and stop streaming, reconfigure (bitrate cap, frame rate, resize to the client window, policies), request an IDR, statistics, goodbye (§14);
- audio, reserved (§15.4).

**Trust.** `hx-session` runs as the desktop user in a container whose software the user controls and which may be compromised; malware there has the same uid as `hx-session`. Everything arriving on the link is **untrusted input** to the internet-facing gatewayd, parsed with explicit limits before allocation (§13, §19). Nothing secret ever goes over the link: no PIN, device key, token, password, client address or device name. The gateway sends only what the desktop needs to render and act: input, display and policy settings, feedback counters.

What malware in the container can do with the link, and why that is acceptable:

| Action | Result |
|---|---|
| Replace or impersonate `hx-session` (listen on the socket path first, or kill it) | It can show the client any picture and cursor, send any clipboard, and observe the input sent to the desktop. All of that is already within its power (it controls the screen and receives the keystrokes anyway); the client treats remote clipboard and links as untrusted (architecture §8.7). |
| Send malformed or oversized data, or flood | Bounded by the §13 limits, the §19 validation and rate limits; a violation drops the link and does not affect gatewayd's other duties. |
| Send decodable-but-malicious video or cursor data | Reaches the client's decoder. Out of scope for the link; noted as a risk (§22, question 8). |
| Reach anything else through the socket | Nothing: the socket is a byte pipe to one gatewayd connection (§11); there is no descriptor passing, and the link carries no authority (no secrets, no path to privd). |

## 11. Transport and socket placement

**Decision: an Incus proxy device, with gatewayd dialling out and `hx-session` listening.**

```
 host                                                    container (unprivileged, isolated idmap)
 hx-gatewayd ──connect──► /run/hx/link/main.sock  ⇄  forkproxy  ⇄  /run/user/1000/hx-session.sock ◄── listen: hx-session
   (uid hx-gatewayd)       (listening socket made by the                 (0600, owned by the desktop user)
                            proxy device, owner hx-gatewayd 0600)
```

- **Container side**: `hx-session` creates and listens on `/run/user/<uid>/hx-session.sock` (the `XDG_RUNTIME_DIR` of the lingering desktop user, which exists on a systemd desktop), mode `0600`, owned by the desktop user. No other account in the container can connect (root in the container can; root there is part of the container's trust domain).
- **Host side**: `hx-privd` adds one proxy device per desktop (`ProvisionSessionLink`, §6.11): `bind=host`, `listen=unix:/run/hx/link/<desktop_id>.sock`, `connect=unix:/run/user/<uid>/hx-session.sock`, host-side socket owned by the gatewayd uid and gid, mode `0600`. `/run/hx/link/` is root:`hx-gatewayd` 0750, so gatewayd can connect but cannot create, rename, replace or delete entries; no other host user can reach it.
- **Direction**: gatewayd connects when it needs the desktop (first authorized client) and `hx-session` accepts. Reasons: (1) the gateway fully controls how many connections exist, which keeps its attack surface at a fixed number of connections per desktop instead of an accept loop that malware can hammer; (2) a gatewayd restart needs no cleanup in the container; (3) `hx-session` idles at about zero cost with no link, and streams only while one exists. When no `hx-session` is listening, the proxy closes the connection at once and gatewayd retries with backoff (§19.2).
- **Why a proxy device, not a shared directory or a socket bind-mounted from the host.** The proxy copies bytes between two sockets it owns, so the container never obtains a kernel-level handle to a host-created socket: no `SCM_RIGHTS` descriptor passing into gatewayd, no peer-credential games, no dependency on how the isolated idmap shows host owners. A bind-mounted directory would also give the container a path on the host filesystem. S3 used a proxy device for its network tests, but nobody has measured its throughput at the media rate (a 20 Mbps ceiling with frames up to 16 MiB), which is one of the items to verify below.
- **Peer identity.** There is none to authenticate on the container side: `SO_PEERCRED` of an accepted connection shows the proxy process, not the gateway, and anything running as the desktop user could connect too, which gives it nothing beyond what it already has (§10). gatewayd does not authenticate `hx-session` either: the host socket path proves "this is the proxy device privd created for this desktop", and the handshake (§12) proves nothing beyond the protocol version. Neither side's decisions rely on the identity of the other. gatewayd reads the link with plain `read`/`recv` and never receives ancillary data; a control message is a violation.
- **To verify during implementation** (1C integration test on a real Incus 6.0.x with an isolated idmap): the exact semantics of the proxy device's `uid`, `gid`, `mode`, `security.uid` and `security.gid` for a unix-to-unix proxy; that connections work after the container is stopped and started; throughput at 20 Mbps with 16 MiB frames. Fallback if `security.uid` does not behave: the container side connects as the container's root (which bypasses the `0600` file mode inside the container's user namespace), with no loss of host-side protection.
- **Rejected alternatives**: a TCP port on the bridge (the bridge's nftables rules and ACL deliberately forbid desktop-to-host traffic; opening a hole for this would weaken the isolation both layers exist to provide); `/dev/incus` or the guest API (`security.guestapi=false` on every desktop); vsock (containers have none; only VMs).

## 12. Connection lifecycle

### 12.1 Lanes

One link is **three** unix connections (lanes) to the same socket path, so that large or slow data never blocks small urgent data. Each lane is a separate byte stream through the proxy.

| Lane | Id | Direction of bulk traffic | Carries |
|---|---|---|---|
| `ctl` | 1 | both, small messages | handshake, control, input, mouse motion, cursor, frame feedback, cancels, statistics, events |
| `media` | 2 | session → gateway | video frames, audio (reserved) |
| `bulk` | 3 | both | clipboard and file transfers |

The gateway to session direction of `media` is unused; a byte received there is a violation.

### 12.2 Preamble and versioning

Each lane starts with an 8-byte preamble from the connecting side (the gateway), followed by a 16-byte `link_id` (random, chosen by the gateway per link, identical on the three lanes). The session answers with the same 8 bytes:

```
 0       4        5        6      7
+--------+--------+--------+------+------+----------------+
| "HXLK" | major  | minor  | lane | 0x00 | link_id (16 B) |   gateway → session
+--------+--------+--------+------+------+----------------+
```

The answer has the first 8 bytes only, with `minor` lowered to the session's if that is lower. Rules:

- The link version is `1.0`. Same major, different minor is accepted; the negotiated minor is the lower one, and a newer minor never sends a message to a peer whose negotiated minor predates it (the rule of protocol.md §4.2). A different major is refused by closing the connection; gatewayd then records `session_outdated` for the desktop and asks privd for `InstallSession` (an update replaced the agent but not the in-container binary).
- `hx-session` accepts at most **one link** (one `link_id`) at a time with at most one connection per lane. A new `link_id` on a `ctl` lane **supersedes** the old link: the old lanes are closed and the session behaves as for link loss (§12.4). A duplicate lane of the current link is closed.
- The gateway opens `ctl` first and waits for the session's `info` (§14.2); it opens `media` and `bulk` after that. If the session does not see both extra lanes within 5 s of `ctl` it drops the link. Preamble and `info` must complete within 5 s of connect, else the gateway closes.
- A malformed preamble, wrong magic, a `lane` outside 1 to 3 or a non-zero reserved byte closes the connection (on the gateway: a violation, §19.2).

### 12.3 Liveness

- The gateway sends `ping` {`nonce`} on `ctl` every 2 s while a link exists; the session answers `pong` within 1 s from its control thread (never from the media path). 10 s without a `pong` and no other `ctl` traffic: the gateway closes the link (a fault, §19.2).
- While streaming, the session also sends `stats` about once per second, which doubles as a heartbeat. An idle desktop produces no frames by design (architecture §6.1), so frame silence is not a liveness signal.
- The session closes the link and stops streaming if it receives nothing from the gateway for 15 s.

### 12.4 Link loss and restart

When the link closes for any reason the session, within 1 s: stops capture and encoding (idle cost about zero), injects **`release_all`** (every held key and button up), aborts transfers, discards queued output, and returns to listening for a new link. It never exits because the link ended. The gateway treats a lost link while a client is connected as `INTERNAL_ERROR`: it sends the client `Goodbye`, then redials with backoff, and the client reconnects to a fresh stream (video restarts from an IDR regardless).

## 13. Framing and limits

After the preamble every lane carries frames:

```
+----------------+---------+------------------------+
| length (u32 LE)| kind u8 | body (length - 1 bytes)|
+----------------+---------+------------------------+
```

The same shape as §4, so one reader implementation serves privd and the link. `length` counts the kind byte and body and is checked against the table **before** allocating. An unknown `kind`, a `kind` not valid on that lane or in that direction, a zero or oversize `length`, a frame truncated by a close, or a protobuf body that fails to decode is a **violation** (§19.2). An unknown *protobuf variant or field* inside a valid message is ignored and counted (forward compatibility).

| Lane | Kind | Direction | Body | Max `length` |
|---|---|---|---|---|
| `ctl` | `0x01` `SessionToGateway` | S → G | protobuf (§14) | 327 685 (the 327 680-byte cursor limit of protocol.md §3.1: a 256 × 256 RGBA shape is 262 144 bytes plus protobuf overhead; plus the kind byte) |
| `ctl` | `0x02` `GatewayToSession` | G → S | protobuf (§14) | 16 384 |
| `media` | `0x10` Video | S → G | media header (20) + payload (§15) | 16 777 237 (16 MiB payload + 20 + kind) |
| `media` | `0x11` Audio | S → G | `seq` u32, `timestamp` u32, Opus packet 1 to 1 100 | 1 110 (reserved, §15.4) |
| `bulk` | `0x20` TransferOpen | both | protobuf `TransferOpen` {`id` u32, `channel` (CLIPBOARD or FILE), `header` = protocol `TransferHeader`} | 4 200 |
| `bulk` | `0x21` TransferData | both | `id` u32 + raw bytes (1 to 65 536) | 65 541 |
| `bulk` | `0x22` TransferEnd | both | `id` u32 | 5 |
| `bulk` | `0x23` TransferAbort | both | `id` u32 + `code` u32 (protocol.md §8 transfer codes) | 9 |

Message-level limits (checked by the **gateway** for S → G and by the session for G → S):

| Item | Limit |
|---|---|
| Strings (`software`, event `message`, `goodbye` `message`) | 128, 256, 256 bytes; control and ANSI characters removed before display or logging |
| `stats` | 4 per second; every counter a bounded integer |
| Cursor shape | at most 256 × 256, `rgba.len == width * height * 4`, hotspot inside the image (protocol.md §5.4); at most 20 shapes per second and 4 MiB of shape data per second |
| Cursor position | coalesced by the gateway to at most one per 1 ms (latest wins); never queued unboundedly |
| `event` | 10 per second |
| Video frame payload | at most 16 MiB; at most 2 × the negotiated `max_fps` frames in any one-second window; at most 4 IDR frames per second |
| Transfers | at most 4 concurrent per direction; one clipboard transfer per direction at a time (a new one aborts the previous); clipboard at most 64 MiB; file at most 4 GiB in v1 (question 7); chunks at most 64 KiB; unread data at most 1 MiB per transfer and 4 MiB per link |
| Input G → S | `InputEvent` at most 1 024 (protocol.md §3.1); input queue 4 096 events |
| Memory per link on the gateway | at most 40 MiB for the lanes combined (a video window of up to 4 frames or 12 MiB, whichever comes first, plus bulk and ctl buffers) |

## 14. Control lane (`ctl`)

Messages are protobuf. They reuse the `hx.v1` types of protocol.md wherever the content is the same (`InputEvent`, `CursorEvent`, `ClientStats`, `TransferHeader`, `VideoCodec`), so field semantics are not defined twice. The new messages below belong to a package `hx.link.v1` (schema location: question 9).

### 14.1 Gateway to session: `GatewayToSession` (`oneof`)

| Variant | Fields | Meaning |
|---|---|---|
| `start` | `epoch` u32, `config` (`StreamConfig`) | Begin streaming for a client. The session creates or resumes the pipeline, replies `stream_format`, and its first frame is an IDR flagged `RESYNC`. `epoch` identifies the client (§18); the controller resets on `start`. |
| `stop` | `epoch` | Stop capturing and encoding within 1 s (the last client left). Keeps listening; clears held keys. |
| `reconfigure` | `config` (`StreamConfig`) | Apply new settings while streaming (client window resize, bitrate cap, frame rate, policies). Zero (unset) fields keep their value, as `ViewConfig` does. |

| `input` | `event` (`hx.v1.InputEvent`) | One validated key, button, scroll or `release_all` event, in client order. |

| Field | Type | Validation (gateway before sending; session again on receipt) | Meaning |
|---|---|---|---|
| `codec` | `VideoCodec` | `H264` in v1; anything else is ignored and answered with `event` `CAPTURE_ERROR` | Codec to produce |

| `width`, `height` | u32 | both 0 (keep) or each 1 to 16 384; the session rounds down to even | Desired remote size from the client window (`Control::request_resize`) |

|---|---|---|
| `info` | `software` (at most 128), `features` u64, `codecs` (repeated `VideoCodec`, at most 4), `display` {`width`, `height`}, `max_fps` u32 | First message on `ctl`. `features` bits: 0 `AUDIO`, 1 `CLIPBOARD`, 2 `FILE_TRANSFER` (the protocol.md §4.3 bits), 8 `INPUT` (XTest available), 9 `RESIZE` (RandR resize available). The gateway uses it for logs, metrics and the admin `Status`; the client protocol has no server-to-client statistics message yet (question 5).

## 15. Media lane (`media`)

### 15.1 Video frame

One `kind 0x10` frame per encoded frame. The body is **exactly** protocol.md §6's 20-byte media header followed by the encoded payload, so the gateway validates the header and then forwards header and payload unchanged as the body of the client's frame stream (channel byte `0x05` first on QUIC; the identical bytes inside a `0x05` message on WebSocket). That keeps the path zero-copy friendly: the gateway reads each frame into one pooled buffer (`bytes::Bytes`) and slices it; it never re-encodes or concatenates.

How the session fills the header:

| Header field | Source |
|---|---|
| `version` | `1` |
| `codec` | `EncodedFrame.codec` mapped to the `VideoCodec` number (H.264 = 1) |
| `flags` | bit 0 `KEY` = `EncodedFrame.idr` (an IDR; a gradual-intra-refresh recovery point does **not** set `KEY`, because `KEY` means "decodes without earlier frames"); bit 1 `RESYNC` = this IDR answers a `start`, a `request_idr`, a `cancel_frames` or a gateway cancel. Other bits 0. |
| `frame_number` | a `u32` counter owned by the link layer, incremented for **every** `EncodedFrame` taken from `Pipeline::frames`, including one dropped before it is written, so a gap means "skipped". It does not follow `EncodedFrame::frame_no` (a `u64` that restarts when the encoder is recreated). Wraps modulo 2^32. |
| `capture_timestamp_us` | the frame's capture time on the container's monotonic clock in microseconds (from `EncodedFrame.timing`, `hx_capture::mono_ns` / 1000); the client only uses differences |
| `payload_len` | `EncodedFrame::bytes().len()` |

Width, height and fps are **not** in the header; they travel in `stream_format` (§14.2).

Gateway validation per frame, before the payload is accepted: `length` within the limit; header present; `version == 1`; `codec` equals the negotiated codec; no reserved flag bits; `payload_len == length - 21`; `frame_number` strictly newer (serial arithmetic) than the last accepted on this link, else drop and count; rate limits of §13. A structural failure is a link violation (§19.2); a rate overage drops the frame. The gateway does **not** decode the payload and does not alter the header (which is why the header is validated, not rewritten).

### 15.2 Backpressure and no unbounded queues

- The gateway **always drains the media lane**: it reads each frame promptly into a pool of at most 4 frames or 12 MiB (§13). It never stops reading because the client is slow, so the session's writer never blocks behind a slow client, and `Pipeline::frames` is never stalled by the network.
- Toward the client, the gateway limits frames in flight to what the transport window allows. When a frame cannot be sent within the window or a budget of about 100 ms, it is **not queued**: the oldest not-yet-delivered frame streams are reset with `STALE_FRAME` (protocol.md §6.2) and reported as `CANCELLED`, and frames never started are reported as `DROPPED`.
- Because H.264 P-frames depend on earlier frames, any cancel or drop breaks the chain. After one, the gateway discards every frame that is not `KEY` until the next `KEY | RESYNC` frame and sends `request_idr` (limited to 2 per second). This is the "cancel queued frame streams and send a fresh full image" rule of architecture §7.4, with the gateway doing the stream resets and the session producing the fresh image.
- The session's own writer must complete each frame it starts (a half-written frame would desynchronise the lane). A write that makes no progress for 2 s closes the lane (a fault).

### 15.3 Acks and cancels (feedback to the congestion controller)

`frame_feedback.results`: one `FrameResult` per frame with `frame_number` u32, `outcome`, `bytes` u32, `elapsed_us` u32 (from the first write to the client until its ack: `FrameAck.elapsed`) and `queued_us` u32 (time the frame waited in the gateway before its first write).

| `outcome` | From `hx_transport::AckOutcome` | Meaning |
|---|---|---|
| `DELIVERED` | `Delivered` | The client received the whole frame (stream completion on QUIC, `0x09` ack on WebSocket) |
| `CANCELLED` | `Cancelled` | The gateway reset the stream (`STALE_FRAME`), by its own decision or on `cancel_frames` |
| `REJECTED` | `Rejected(code)` | The client stopped the stream |
| `DROPPED` | (gateway only) | The gateway discarded the frame without starting to send it (window full, no client, resync discard) |

`ConnectionLost` is not sent; the client connection ending is followed by `stop`. Feedback arrives on `ctl`, so a congestion signal is never stuck behind video. The session's controller (1F) uses `elapsed_us`, `queued_us`, the `DELIVERED` rate and the `CANCELLED`/`DROPPED` counts to step its bitrate ladder (S2: settled near 3.5 Mbps at 150 ms RTT, 10 Mbps and 1% loss) and to decide when to send `cancel_frames` and force a `RESYNC` IDR. Feedback for one frame is sent at most once; a result for an unknown frame number is ignored by the session.

### 15.4 Audio (reserved)

`kind 0x11` is the protocol.md §7.2 datagram body (`seq`, `timestamp`, one Opus packet, 10 ms frames) as a media-lane frame. It is not produced in Phase 1: the `AUDIO` feature bit is 0 in `info`, and a `0x11` frame while the feature was not negotiated is a violation. Audio is loss tolerant: the gateway forwards it as a datagram and drops it rather than queueing it.

## 16. Bulk lane (`bulk`)

Clipboard and files use the transfer shape of protocol.md §9.4 (header, data chunks, end, abort) on one lane, so many transfers share one low-priority connection and cannot delay anything else.

- **IDs**: the gateway allocates odd ids and the session even ids; an id already in use is a violation. `TransferOpen.channel` is `CLIPBOARD` (protocol channel `0x07`) or `FILE` (`0x08`); its `header` is the protocol `TransferHeader` (`mime`, `name`, `size`) under the same validation (printable-ASCII `mime`, the file-name rules of protocol.md §3.1, empty `name` for the clipboard). The gateway applies those rules to every header the session sends **before** it opens a client stream.
- **Size**: the receiver counts bytes; fewer or more than `size`, or a clipboard over 64 MiB, aborts that transfer (`TRANSFER_ERROR`) and the lane continues. File limit 4 GiB in v1 (the protocol sets none yet; question 7).
- **Flow control**: a byte stream gives per-lane, not per-transfer, flow control. The gateway reads a transfer's data only while it holds less than 1 MiB unread for it and 4 MiB for the link, so a stalled client stream pauses the bulk lane and never `ctl` or `media`. One slow transfer can delay other transfers; accepted.
- **Policy**: the gateway enforces the device's clipboard and file settings in both directions (drops the data and aborts), and also tells the session through `StreamConfig` so that it does not read the selection at all. Clipboard transfers from the session are limited to 4 per second.
- **Names are hints.** The session writes received files into a directory of its own choosing (`~/Downloads/hx-received/`), picks its own file name, never overwrites (`O_EXCL`), never follows symlinks (`O_NOFOLLOW`), and creates the file with mode `0600`. The gateway never treats a name as a path, and forwards the session's names to the client only as display hints, after the protocol.md name validation.

## 17. Priorities and backpressure

The requirement: **input never waits behind video**, and video is dropped or cancelled, never queued without bound.

1. **Lanes separate sizes.** Video (up to 16 MiB), cursor shapes and transfers each have their own connection or direction; `ctl` G → S carries only messages of at most 16 KiB.
2. **The gateway's writer for `ctl` G → S** is a single task with queues drained in strict order: **P0** `input` events (ordered, bounded at 4 096; overflow means the client is abusing the channel and it is closed with `PROTOCOL_ERROR`), then the single-slot **`mouse`** (latest wins: a newer motion replaces an unsent one, absolute and relative merged as in protocol.md §7.1, `MouseCoalescer`); **P1** `frame_feedback`, `request_idr`, `reconfigure`, `start`/`stop`, `ping`; **P2** `transport_stats`, `client_stats`, `goodbye`. A key or button always goes out before pending motion that arrived after it. Button events carry absolute coordinates, so a coalesced motion cannot misplace a click.
3. **The session's reader for `ctl` G → S** runs on its own thread, independent of the encode pipeline, and injects input with the XTest backend straight from it. The encoder threads cannot delay input.
4. **The gateway's reader for `ctl` S → G** parses cursor, `stream_format`, `cancel_frames` and `stats` in a task separate from the media reader and the bulk reader. Cursor positions coalesce to the newest within 1 ms; a shape is never overtaken by a later position (the protocol.md ordering rule).
5. **Video**: drained promptly, bounded window, cancel or drop with feedback, resync by IDR (§15.2). **Bulk**: lowest priority; the gateway yields after every 256 KiB so it cannot monopolise the runtime.

## 18. One active client per desktop and takeover

v1 has one active client per desktop. The session link knows clients only through `epoch` (§14.1); all policy sits in gatewayd.

- A second client that authenticates (pinned key and PIN passed) while another is active **takes over**, subject to a per-server policy `takeover` ∈ `allow` (default) or `deny` (the newcomer is answered `BUSY`). The default is `allow` because a user switching devices must not be locked out by their own stale session; both clients have passed authentication, and the displaced one is told.
- Takeover sequence in gatewayd, in this order: (1) stop forwarding the old client's input and send `input{release_all}` to the session; (2) cancel the old client's in-flight frames (`CANCELLED`) and abort its transfers (`TransferAbort`); (3) tell the old client it was displaced: `Goodbye` with code `BUSY` and a message naming the new device (sanitized), until a dedicated `TAKEN_OVER` close code exists in protocol.md §8 (question 4); (4) increment `epoch` and send `start{epoch, config}` for the new client, then expect `stream_format` with the same `epoch` and an IDR `RESYNC` frame. Frame numbers keep counting, so the new client's reorder window starts clean.
- The session resets its congestion controller on `start`, discards feedback tagged for earlier frames and re-sends the cursor shape. Clipboard and transfers are per client and are not carried across.
- Only the current `epoch` may send input to the session: gatewayd forwards nothing from a client that is not the active one.
- When the last client leaves, gatewayd sends `stop`, keeps the link for 30 s (so a reconnect is instant), then closes `bulk`, `media` and `ctl`. The next authorized client redials.

## 19. Untrusted input and fault handling

### 19.1 Rules gatewayd follows for every session-supplied byte

1. Lengths are checked against §13 **before** any allocation; buffers come from fixed pools; no allocation is sized by a session-supplied value beyond those limits.
2. All integers are range-checked (frame numbers, sizes, `payload_len == length - 21`, coordinates, counters); statistics use saturating arithmetic.
3. Strings are length limited and sanitized (control and ANSI characters removed) before they reach a log, the admin API or a client; session-supplied text is never used as a path, command or URL.
4. Cursor, transfer-header and file-name content gets the same validation as when a client sends it (protocol.md §3.1, §5.4, §5.5), before any of it is forwarded to a client.
5. Unknown protobuf fields and `oneof` variants are ignored and counted; undecodable bodies are violations.
6. Rates are enforced per message class (§13); the gateway never spends unbounded CPU or memory because the session is chatty.
7. The gateway never sends anything secret to the session, and never derives behaviour from where the session says it is, who it says it is, or what version string it claims, beyond the protocol version already negotiated.
8. No descriptors, no ancillary data; the lanes are read with plain `read`.
9. Fuzz targets for 1H: the lane framer, `SessionToGateway` decoding, media-header validation, `TransferOpen` validation, cursor-shape validation.

### 19.2 Faults and recovery

A **violation** (malformed frame or preamble, forbidden kind, oversize length, structural media-header error, a byte on an unused direction) or a sustained rate overage (3 consecutive seconds) closes all three lanes, increments a per-link fault counter, logs a rate-limited warning with the sanitized reason, sends the client `Goodbye(INTERNAL_ERROR)` if one is connected, and leaves gatewayd otherwise unaffected. Redialling uses exponential backoff 1, 2, 4, … up to 30 s. After 5 faults within 10 minutes gatewayd asks privd for `RestartSession` (class A, so rate limited by privd); after 3 restarts in an hour it stops redialling and reports the desktop as `session_unavailable` in status, so the app can say so (a bad session package or malware, the user's call). A violation never crashes gatewayd: parse errors are values.

## 21. Implementation notes and gaps

Not part of the contract; for the people implementing it.

1. **Schema location.** Both IPC contracts are internal to one release, so their protobuf need not live in the public client schema. Proposal: a new workspace crate `hx-ipc` holding the framing (§4, §13), the `hx.privd.v1` and `hx.link.v1` messages and helpers, shared by `hx-gatewayd`, `hx-privd`, the CLI and `hx-session` (it must not pull in `quinn`). That adds a crate to architecture §3 and dependencies to tech-stack.md (`zeroize`, an HPKE implementation, `rustix` for `SO_PEERCRED` and `mlock`); both documents change in the branch that adds the crate.
2. **`hx-provision` gaps** (1D): (a) a device-add call on the Incus client for the proxy device (§6.11); (b) a standalone password-change entry point built on the post stage's stdin-file mechanism (§6.9); (c) setting limits on a live instance, including the root disk size (§6.8); (d) recipe vars for `settings`: hostname, timezone, locale, keyboard (§6.5); (e) the Docker disable path (§6.9) and the host-network-only fallback; (f) teardown helpers that delete only marked objects (§6.13). Until they exist the matching commands return `UNIMPLEMENTED`, or privd uses `Client` methods directly.
3. **Unit naming.** The recipe's `hx-session.service` currently runs `xfce4-session`. The streaming daemon needs another unit name (for example `hx-stream.service`), enabled with `systemctl --global enable`; `InstallSession` and `RestartSession` use that name.
4. **Resumed installs.** The installer's resume (architecture §5.3) re-calls idempotent commands; the app resends the password after a gatewayd restart.
5. **Version coupling.** gatewayd, privd, the CLI and the in-container `hx-session` ship from one release. The link tolerates a minor mismatch only; after an update gatewayd calls `InstallSession` for any desktop reporting an older major.

## 22. Open questions for review

Decisions the reviewer should challenge.

1. **Device registry in gatewayd, not privd** (§2). It keeps pre-auth data out of root and lets revocation close live sessions, but a compromised gatewayd can add its own device. The alternative (registry in privd, gatewayd asks on every connection) adds a round trip and a root-side parser for no real gain against a compromised gatewayd, which relays the desktop anyway. Is that argument convincing?
2. **Keeping the Drive token and backup key out of gatewayd needs sealing to a privd key** (§5.2), and the client must learn privd's public key through an authenticated path. That needs a change in 1B's pairing exchange (for example the key included in the SPAKE2-confirmed transcript). Until then the architecture claim "gatewayd never sees the Drive token" (§8.6) cannot be met, because the paired channel terminates at gatewayd. It is a Phase 2 blocker; in Phase 1 the password is plain, so gatewayd sees it in transit. Accept, or require sealing of the password too?
3. **Setup window** (§5.1): the gateway may create the host and desktop only while an Admin-opened window is open, up to 24 hours. Is a window the right control, or should the installer perform stages 4 to 8 itself as root, with the app only displaying progress? The latter removes gatewayd's setup power entirely but means the installer needs the wizard's secrets, which the architecture says arrive over the paired channel.
4. **Takeover policy** (§18): default `allow`, last authenticated wins, the displaced client told with `Goodbye(BUSY)`. protocol.md needs a `TAKEN_OVER` close code (note for its owner; not edited here). Is `allow` the right default?
5. **No server-to-client statistics message in protocol.md**: the stats overlay of architecture §11.1 needs one (the gateway has `SessionStats` and `transport_stats`). Note for the protocol owner.
6. **Docker enable from the Gateway role** (§6.9): it reduces container isolation, and a compromised gatewayd could trigger it (with the acknowledgement flag) to make a later container escape easier. Mitigations are the flag, logging, a 3 per hour rate and the roll-back; the alternative is Admin-only plus a CLI step. Acceptable for v1?
7. **File size limit** of 4 GiB (§13, §16): protocol.md sets a limit only for the clipboard (64 MiB). Needs agreement; the transfer UI and the gateway's per-link bounds assume it.
8. **A hostile session can feed the client's video decoder** (§10): the gateway does not decode, so a crafted H.264 stream or cursor reaches libavcodec in the client. Should the gateway at least check NAL structure (Annex B framing), accepting the CPU cost? A fuzz-and-sandbox answer in the client (1G/1H) may be better.
9. **Where the schemas live**: a new `hx-ipc` crate (§21, note 1) versus `crates/hx-proto/proto`. Affects who owns the contract and the crate dependency graph.
10. **Proxy device semantics** (§11): the `uid`, `gid`, `mode` and `security.*` behaviour of unix-to-unix proxies on Incus 6.0 with isolated idmaps, and their throughput at the media rate, are assumed from the documentation and must be verified before implementation; the fallback is stated.
11. **Several desktops**: with one desktop per server (v1) a single gateway-side socket suffices. Per-desktop listen paths already exist (§11), but the missing isolation between desktops on one bridge (architecture §4.2, "Known limit") is separate and unsolved.
12. **Network access by the update fetcher and image fetcher** (§6.5, §6.12) is specified as a sandboxed child so that root never makes HTTP requests; the sandbox profile and the exact signature scheme for prebuilt images belong to 1C and 1D and are not specified here.
